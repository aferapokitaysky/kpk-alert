# Технічне завдання: Windows-вузол оповіщення

## 1. Призначення документа

Документ описує вимоги до Windows-вузла KGTA Alert, який встановлюється на комп’ютері корпусу, підключеному до системи гучномовців. Його можна використовувати як окреме завдання для реалізації на іншому комп’ютері.

Основна вимога: вузол має приймати команди лише від Watcher через взаємну TLS-автентифікацію, перевіряти їх, відтворювати заздалегідь підготовлені локальні аудіофайли та передавати серверу фактичний стан виконання. Втрата мережі не повинна спричиняти повторне відтворення старих команд після їх завершення або закінчення строку дії.

Це ТЗ спирається на актуальні контракти в `src/Watcher.Contracts/DeviceCommands` та API Watcher. Файл концепції системи є джерелом вимог і побажань, але твердження, що суперечать реалізованому API або цьому документу, не слід переносити в код без окремого ADR.

Зокрема, концепт згадує SignalR, пряме опитування alerts.in.ua з кожного ПК, локальний аварійний PIN і власну матрицю пріоритетів. Поточний транспорт пристроїв — WSS із серверною автентифікацією mTLS; API провайдерів і їх секрети залишаються на Watcher; локальний PIN і числовий priority не входять до контракту команди. Такі відмінності є свідомими межами першої версії, а не деталями, які Windows-клієнт має вгадати.

## 2. Результат розробки

Потрібно створити Windows-рішення з двох окремих процесів:

1. **Фонова Windows-служба** — мережа, mTLS, WebSocket, SQLite, валідація команд, черга квитанцій, запуск і зупинка аудіо.
2. **Локальна панель оператора** — показ стану служби, з’єднання, аудіовиходу, останніх команд і діагностики. Панель спілкується зі службою через локальний Named Pipe та не має доступу до приватного ключа пристрою.

Закриття панелі, вихід користувача з Windows або блокування робочого столу не повинні завершувати службу. Служба не показує вікон і не вимагає інтерактивного входу.

## 3. Межі першої версії

### Входить до першої версії

- Windows-служба з автоматичним запуском після завантаження ОС.
- Перевірка серверного сертифіката й клієнтський сертифікат пристрою через mTLS.
- Отримання серверної ідентичності пристрою через `GET /api/v1/device/identity`.
- Вихідний WebSocket до `GET /api/v1/device/commands/stream`.
- Валідація контракту `CommandDispatch` версії 1.
- Локальна SQLite-база з дедуплікацією команд, sequence та надійною чергою квитанцій.
- Відтворення затверджених локальних аудіофайлів із визначеного аудіовиходу.
- Жорстке обмеження тривалості відтворення до значення `maxPlaybackDurationSeconds`, не більше 900 секунд.
- Підтвердження станів через `POST /api/v1/device/command-receipts`.
- Автоматичне відновлення WebSocket і надсилання збережених квитанцій після відновлення мережі.
- Локальна панель діагностики без зберігання облікових даних користувача.
- Установник, видалення, оновлення, журнали Windows і перевірка працездатності після перезавантаження.

### Не входить до першої версії

- Пряме підключення Windows-вузла до API повітряних тривог або зберігання на ньому токенів провайдерів. Джерела та резервування провайдерів обробляє сервер Watcher.
- Локальне автоматичне створення команд, коли сервер недоступний.
- Автономний PIN для запуску сигналу, локальні ролі й локальний вхід через Google.
- Керування розкладом дзвінків, оголошеннями, мікрофоном або фоновим радіо.
- Отримання та встановлення нових аудіофайлів через API, доки не буде затверджено серверний контракт маніфесту й пакетів файлів.
- Самостійне правило пріоритету, яке визначається назвою сценарію або локальною конфігурацією.

Ці функції можуть бути окремими етапами. Не вмикати їх через приховані перемикачі чи незадокументовану поведінку.

## 4. Блокери серверного контракту

Наведені нижче залежності треба закрити до повного наскрізного запуску на реальному корпусі.

### 4.1. Отримання локальних аудіосценаріїв

Команда `CommandDispatch` містить `presetCode` і SHA-256 `manifestHash`, але поточний API пристрою не надає маніфест чи аудіофайли. API оператора `GET /api/v1/presets` повертає лише назву та код сценарію і не призначений для пристроїв.

До появи окремого mTLS-контракту розробка використовує тестові локальні пакети. Production-вузол не можна запускати, якщо локальний файл сценарію відсутній або його маніфест не збігається з хешем у команді.

Для серверної інтеграції окремо погодити й реалізувати:

- endpoint пристрою для отримання лише опублікованого маніфесту його локації;
- endpoint завантаження окремого файлу лише за серверним `assetId`, без довільних URL і файлових шляхів;
- формат канонічного JSON маніфесту та спосіб обчислення `manifestHash`;
- SHA-256, розмір, формат і допустиму тривалість кожного файлу;
- атомарне встановлення нової версії пакета та повернення до попередньої працездатної версії.

Передавання байтів файла через WebSocket заборонене. Усі аудіофайли зберігаються локально до отримання команди.

### 4.2. Команда зупинки

DTO версії 1 описує `action: "stop"` із `targetCommandId`, але API оператора наразі створює лише `start`.

Коли вузол прийняв команду зупинки, він надсилає `accepted`, а після зупинки цільового відтворення — `completed` із `commandId` саме команди `stop`. Сервер перевіряє збережений `targetCommandId`, пристрій, локацію та послідовність і в одній транзакції завершує команду зупинки та переводить активну цільову доставку `start` у `Stopped`. Не надсилати `stopped` для ID команди `stop`: цей стан належить доставці команди `start`. Якщо відтворення завершилося локально або за таймером до команди зупинки, вузол може надіслати `stopped` для вихідної команди `start`.

API оператора ще не створює команду `stop`; до його реалізації вузол має покрити цю локальну семантику тестами, але production-зупинку через сервер не вважати доступною. Не підміняти зупинку створенням `start` із порожнім файлом.

## 5. Рекомендований стек і структура solution

Використовувати той самий major .NET SDK, що й серверна частина репозиторію. Поточні проєкти solution цілляться в .NET 10; якщо інший комп’ютер має інший SDK, спершу встановити версію з `global.json`, а не знижувати target framework самостійно.

Рекомендована структура:

```text
src/
  Watcher.EdgeAgent.Contracts/       # локальні моделі IPC і конфігурації
  Watcher.EdgeAgent.Core/            # перевірка команд, стани, межі відтворення
  Watcher.EdgeAgent.Infrastructure/  # SQLite, HTTP, WebSocket, сертифікати, файли
  Watcher.EdgeAgent.Service/         # Host Windows Service та життєвий цикл
  Watcher.EdgeAgent.Desktop/         # WPF-панель діагностики
tests/
  Watcher.EdgeAgent.UnitTests/
  Watcher.EdgeAgent.IntegrationTests/
```

Кожен проєкт додається до наявного `KgtaAlert.slnx`. Не копіювати серверні класи всередину Windows solution. DTO `CommandDispatch`, `CommandReceipt`, enum та `DeviceCommandValidator` мають надходити з `Watcher.Contracts` через спільний пакет або project/package reference. Якщо вузол збирається окремо, узгодити версіонований NuGet-пакет контрактів; вручну дублювати DTO заборонено.

Служба працює як Windows Service, а не як WPF-процес, запущений «для автозапуску». WPF рекомендовано використовувати лише для локального статусного екрана. Не використовувати інтерактивну службу Windows.

## 6. Взаємодія процесів

### 6.1. Windows-служба

Служба відповідає за:

- читання й перевірку конфігурації;
- SQLite і міграції локальної БД;
- зберігання та використання клієнтського сертифіката;
- mTLS HTTP-запити і WebSocket;
- перевірку контракту й строку дії команди;
- збереження `commandId` та `sequence` до зовнішнього ефекту;
- аудіопотік, таймер максимальної тривалості та зупинку;
- збереження квитанцій до підтвердження сервером;
- журнал Windows Event Log і локальні метрики діагностики.

### 6.2. Панель оператора

Панель має показувати:

- стан служби та час останнього запуску;
- стан mTLS/WebSocket: «Підключення», «Працює», «Повторне підключення», «Не налаштовано»;
- серверний `deviceId` і `locationId` після успішного identity-запиту;
- вибраний аудіовихід та його доступність;
- поточний стан аудіо: «Очікує», «Відтворює», «Зупинено», «Помилка»;
- останній `commandId`, його sequence та стан підтвердження;
- кількість квитанцій, що очікують відправлення;
- точну зрозумілу причину останньої помилки та дію для відновлення.

Панель не показує приватний ключ, сертифікат у форматі PFX, секрети, повний HTTP-заголовок Authorization, тіла зовнішніх відповідей або stack trace.

У першій версії панель не має кнопок ручного запуску/зупинки сигналу. Екстрені команди створюються через авторизований вебпульт Watcher. Локальні керувальні дії потребують окремої моделі авторизації та аудиту.

### 6.3. Локальний Named Pipe

- Ім’я pipe: `KGTA.Alert.EdgeAgent.Control`.
- Pipe доступний тільки на локальному комп’ютері; TCP listener для IPC не створюється.
- ACL дозволяє підключення службі, локальним адміністраторам і визначеній групі операторів читати стан.
- Кожне IPC-повідомлення має версію схеми, тип операції та обмежений розмір; довільна десеріалізація типів заборонена.
- Якщо локальне керування з’явиться пізніше, кожна команда IPC проходить окрему авторизацію; приховування кнопки у WPF не є контролем доступу.
- Розрив pipe не впливає на WebSocket, SQLite чи відтворення.

## 7. Конфігурація вузла

Конфігурація поділяється на нешкідливі параметри та секрети.

### Нешкідливі параметри

Зберігаються у файлі конфігурації з ACL для читання служби:

```json
{
  "Server": {
    "BaseUrl": "https://notify.example.edu.ua",
    "WebSocketPath": "/api/v1/device/commands/stream",
    "IdentityPath": "/api/v1/device/identity",
    "ReceiptPath": "/api/v1/device/command-receipts"
  },
  "Transport": {
    "ReconnectInitialDelaySeconds": 1,
    "ReconnectMaximumDelaySeconds": 30,
    "ReceiptRetryInitialDelaySeconds": 1,
    "ReceiptRetryMaximumDelaySeconds": 60,
    "MaximumClockSkewSeconds": 120,
    "MaximumWebSocketMessageBytes": 32768
  },
  "Audio": {
    "EndpointId": "",
    "RootDirectory": "C:\\ProgramData\\KGTA\\Alert\\Audio",
    "DefaultVolume": 1.0
  },
  "Storage": {
    "DatabasePath": "C:\\ProgramData\\KGTA\\Alert\\edge-agent.db",
    "MaximumReceiptQueue": 10000
  }
}
```

Цей JSON є прикладом структури, а не фактичним hostname чи production-конфігурацією. Серверний base URL має бути заданий адміністратором установника або захищеної локальної конфігурації; node не приймає довільний URL з команди. Дозволені лише HTTPS/WSS та відомий домен Watcher.

### Секрети та сертифікати

- Приватний ключ пристрою створюється або імпортується в Windows Certificate Store з приватним ключем, неекспортованим після сполучення, якщо це підтримує виданий тип ключа.
- Доступ до ключа має лише SID служби й адміністратор для ротації. Панель не отримує handle до приватного ключа.
- PFX не залишається в робочому каталозі, завантаженнях, журналах чи резервних копіях.
- Сертифікат сервера перевіряється системним ланцюжком довіри й hostname. Callback, що безумовно повертає `true`, заборонений.
- Не вимикати перевірку відкликання сертифіката в production. Якщо CRL/OCSP недоступні, поведінка задається deployment ADR; не замінювати її мовчки режимом `NoCheck`.
- Серверний токен провайдера тривог не зберігається на пристрої.

## 8. Ідентифікація та протокол з Watcher

### 8.1. Сполучення пристрою

Поточний сервер очікує вже створений запис `Device` із SHA-256 відбитком сертифіката. Повний процес першого сполучення й видачі сертифіката ще не входить у готовий API.

Для інтеграційного стенда відповідальний адміністратор окремо реєструє пристрій, корпус і сертифікат. Не створювати в Windows-клієнті власний pairing endpoint чи постійний API key.

### 8.2. Перевірка ідентичності

Після запуску служба виконує `GET /api/v1/device/identity` через mTLS. Відповідь:

```json
{
  "deviceId": "00000000-0000-0000-0000-000000000000",
  "locationId": "00000000-0000-0000-0000-000000000000"
}
```

Зберегти отримані значення як серверну ідентичність. Перед кожною командою перевіряти, що `deviceId` збігається з нею, `locationId` збігається з прив’язкою локального аудіопакета, а сертифікат і локація не відкликані сервером. Не приймати device/location identity з локального JSON як доказ серверної особи.

### 8.3. WebSocket

- Встановити WSS на окремий mTLS listener сервера: `/api/v1/device/commands/stream`.
- Клієнтський сертифікат передається під час TLS handshake. Cookie, bearer token у URL і query secret не використовуються.
- Сервер надсилає JSON `CommandDispatch` текстовими WebSocket frames.
- Канал є одностороннім на рівні прикладного протоколу. Будь-які клієнтські data frames заборонені; квитанції надсилаються окремим HTTPS POST.
- Обмежити розмір одного повідомлення значенням конфігурації та жорстким верхнім максимумом 32 KiB. Якщо повідомлення перевищує межу, закрити канал і записати `oversized_message` без логування тіла.
- Встановити transport keep-alive, обробляти нормальне закриття, timeout, TLS-помилку та некоректний JSON окремо.
- WebSocket reconnect використовує exponential backoff із jitter і верхньою межею 30 секунд. Після мережевого відновлення не запускати команди, які вже прострочені.
- Відсутність додаткового Heartbeat-повідомлення не означає, що вузол працездатний; перша версія панелі може достовірно показувати лише стан транспортного з’єднання та останню локальну аудіоподію.

## 9. Контракт команди

Актуальна модель знаходиться в `Watcher.Contracts.DeviceCommands.CommandDispatch`:

```json
{
  "schemaVersion": 1,
  "commandId": "00000000-0000-0000-0000-000000000001",
  "deviceId": "00000000-0000-0000-0000-000000000002",
  "locationId": "00000000-0000-0000-0000-000000000003",
  "sequence": 42,
  "action": "start",
  "presetCode": "air_raid",
  "manifestHash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "issuedAtUtc": "2026-11-05T09:00:00Z",
  "expiresAtUtc": "2026-11-05T09:05:00Z",
  "maxPlaybackDurationSeconds": 900,
  "targetCommandId": null
}
```

Вузол має перевіряти до будь-якого аудіоефекту:

1. JSON відповідає DTO версії 1; невідома версія не виконується.
2. `commandId`, `deviceId`, `locationId` не порожні, а `sequence` більше нуля.
3. `deviceId` збігається з `GET /api/v1/device/identity`; `locationId` збігається із серверною локацією цього пристрою.
4. `issuedAtUtc` та `expiresAtUtc` мають UTC offset 0, `expiresAtUtc > issuedAtUtc`, а час локальної машини синхронізований. Команду відхиляти, якщо `now >= expiresAtUtc`.
5. `sequence` строго більший за останню прийняту послідовність для локації, крім точного повтору того самого `commandId`.
6. `action` є тільки `start` або `stop`; регістр і рядкові enum-значення відповідають спільному DTO.
7. Для `start`: `presetCode` має формат `[a-z0-9_]{1,80}`, `manifestHash` — рівно 64 hex-символи, `targetCommandId` відсутній, тривалість у межах 1–900 секунд.
8. Для `stop`: `presetCode` та `manifestHash` відсутні, `targetCommandId` не порожній, тривалість дорівнює нулю.
9. Локальний пакет є опублікованим/дозволеним для локації, його маніфест збігається з `manifestHash`, а файл існує та проходить власну SHA-256 перевірку.

Поля на кшталт довільного URL, абсолютного шляху, команди оболонки, гучності за межами локальної політики, priority від клієнта чи імені оператора відсутні в контракті й не мають прийматися через додаткову десеріалізацію.

## 10. Правила SQLite та ідемпотентності

Локальна база зберігається у `ProgramData`, а не в каталозі користувача чи директорії встановлення. Увімкнути foreign keys, транзакції та WAL, задати busy timeout. Міграція виконується під час запуску служби до підключення до Watcher.

### 10.1. Рекомендовані таблиці

#### `processed_commands`

| Поле              | Тип           | Обмеження                   |
| ----------------- | ------------- | --------------------------- |
| `command_id`      | UUID/TEXT     | primary key                 |
| `device_id`       | UUID/TEXT     | not null                    |
| `location_id`     | UUID/TEXT     | not null                    |
| `sequence`        | INTEGER       | not null, > 0               |
| `action`          | TEXT          | `start` або `stop`          |
| `payload_hash`    | TEXT          | SHA-256 канонічного payload |
| `state`           | TEXT          | локальний стан команди      |
| `received_at_utc` | TEXT          | UTC                         |
| `updated_at_utc`  | TEXT          | UTC                         |
| `expires_at_utc`  | TEXT          | UTC                         |
| `diagnostic_code` | TEXT nullable | лише код, не stack trace    |

Унікальність `command_id` обов’язкова. Повторний `command_id` з тим самим `payload_hash` є повторною доставкою; повернути попередній локальний стан і не запускати звук повторно. Повторний ID з іншим payload — порушення контракту: записати security event і закрити з’єднання без виконання.

#### `location_sequences`

| Поле             | Тип       | Обмеження      |
| ---------------- | --------- | -------------- |
| `location_id`    | UUID/TEXT | primary key    |
| `last_sequence`  | INTEGER   | not null, >= 0 |
| `updated_at_utc` | TEXT      | UTC            |

Оновлення послідовності й вставлення `processed_commands` виконуються атомарно в одній транзакції. Нижча або повторно використана послідовність не запускає аудіо.

#### `receipt_outbox`

| Поле                  | Тип           | Обмеження                         |
| --------------------- | ------------- | --------------------------------- |
| `event_id`            | UUID/TEXT     | primary key; генерується один раз |
| `command_id`          | UUID/TEXT     | not null                          |
| `sequence`            | INTEGER       | not null                          |
| `state`               | TEXT          | значення `CommandReceipt`         |
| `occurred_at_utc`     | TEXT          | незмінний UTC-час події           |
| `diagnostic_code`     | TEXT nullable | формат `[a-z0-9_]{1,64}`          |
| `attempt_count`       | INTEGER       | >= 0                              |
| `next_attempt_at_utc` | TEXT          | UTC                               |

Повний набір полів квитанції після першої вставки незмінний. На кожному повторі HTTP-запиту використовувати ті самі `eventId`, `commandId`, sequence, state, `occurredAtUtc` і `diagnosticCode`. Підтверджену квитанцію видалити або позначити відправленою в тій самій локальній транзакції.

#### `active_playback`

У першій версії одночасно дозволено не більше одного активного відтворення на аудіовихід. Таблиця містить `command_id` (unique), `preset_code`, `started_at_utc`, `deadline_at_utc`, `last_known_state`. Вставлення/зміна стану пов’язана з `processed_commands` транзакціями.

### 10.2. Порядок виконання Start

1. Прочитати та повністю перевірити команду, час, identity, sequence, маніфест і файл.
2. Почати транзакцію SQLite; перевірити повтор `commandId` і останню sequence.
3. Зберегти команду в стані `accepted`, оновити `last_sequence`, створити квитанцію `accepted` із новим `eventId`.
4. Commit транзакції. Лише після цього перейти до аудіо API.
5. Відкрити локальний файл та запустити вихідний аудіопотік. Після підтвердженого старту записати `playing` і квитанцію `playing`.
6. Після природного завершення або досягнення deadline зупинити потік, записати фінальний стан і квитанцію.

Фізичне відтворення та SQLite не можна об’єднати в одну атомарну транзакцію. Щоб не повторити сигнал після аварійного завершення процесу, під час старту служби всі незавершені `accepted`/`playing` команди перевести в `failed` із кодом `agent_restart`; повторно автоматично не відтворювати їх. Записати квитанцію, якщо сервер ще приймає перехід; відхилення квитанції не є дозволом відтворити команду повторно.

## 11. Стани й квитанції

Використовувати спільні значення `DeviceCommandState`:

| Стан        | Значення для вузла                                                                       |
| ----------- | ---------------------------------------------------------------------------------------- |
| `accepted`  | Команду перевірено й записано в SQLite до зовнішньої дії. Це ще не означає, що звук іде. |
| `playing`   | Аудіопотік відкрито й відтворення фактично почалося.                                     |
| `completed` | Локальний файл завершився природно або встановлене відтворення завершено.                |
| `stopped`   | Адресоване активне відтворення зупинено явною stop-командою.                             |
| `rejected`  | Команда не пройшла перевірку до прийняття; потрібен короткий код причини.                |
| `failed`    | Команда прийнята, але аудіо або інфраструктурна дія не виконана; потрібен короткий код.  |
| `expired`   | `now >= expiresAtUtc` до початку відтворення; потрібен короткий код.                     |

`CommandReceipt` має містити `schemaVersion: 1`, новий стабільний `eventId`, точні `commandId` і `sequence`, рядковий стан, UTC `occurredAtUtc` і код причини для `rejected`, `failed` та `expired`. Код причини не містить текст винятку або персональних даних. Приклади кодів: `invalid_payload`, `wrong_device`, `stale_sequence`, `command_expired`, `preset_missing`, `manifest_mismatch`, `audio_output_unavailable`, `audio_start_failed`, `agent_restart`.

Допустимі переходи сервер перевіряє окремо. Якщо сервер відповів `409`, не змінювати вміст старої квитанції й не генерувати новий `eventId` для тієї самої події. Зберегти технічний код конфлікту локально та перевести інтеграцію в діагностичний стан; повторити тільки після визначеної політики синхронізації.

## 12. Доставка квитанцій

- Відправляти найстарішу due-квитанцію першою; порядок для одного `commandId` зберігати.
- `202 Accepted` означає, що сервер записав квитанцію; `200 OK` із `duplicate: true` означає, що точний повтор уже оброблено. Обидві відповіді підтверджують видалення/позначення квитанції як доставленої.
- Тимчасові помилки мережі, `408`, `429` та `5xx` повторювати з exponential backoff і jitter. `Retry-After` має перевагу, якщо валідний і обмежений локальним максимумом.
- `400` означає дефект локального контракту: не повторювати без зміни коду, зафіксувати помилку й показати її в панелі.
- `401`/`403`/помилка TLS означають, що ідентичність або сертифікат не прийняті. Не змінювати сертифікат автоматично й не вимикати перевірки; очікувати адміністративного втручання.
- `404` означає невідомий або відкликаний сервером пристрій/команду. Не видаляти історію локально; записати код і припинити повтори цієї квитанції до звірки identity.
- Кількість елементів outbox обмежити. Якщо межу досягнуто, не видаляти непідтверджені квитанції; перейти в degraded state і повідомити оператора.

## 13. Аудіопідсистема

### 13.1. Вихідний пристрій

- Під час інсталяції або через панель адміністратор обирає конкретний Windows audio endpoint.
- Зберігати стабільний endpoint ID, а не лише його локалізовану назву.
- Якщо вибраний endpoint відсутній, не перемикатися непомітно на HDMI/навушники/інший пристрій. Команду не запускати, записати `audio_output_unavailable` і показати точний стан.
- Втрата пристрою під час відтворення завершує команду помилкою; при появі endpoint не продовжувати стару команду з початку.
- Прототип має перевірити вихід без входу користувача, після reboot, після блокування екрана, при відключенні/підключенні USB-пристрою та після рестарту Windows Audio Service.

Windows-служби працюють у Session 0 і не мають створювати GUI; нова служба не повинна взаємодіяти з робочим столом користувача. Для аудіо використовується системний WASAPI endpoint, однак доступність потрібного виходу в Session 0 залежить від цільової ОС, драйвера й обладнання. До розробки UI треба зібрати короткий технічний spike на цільовому ПК: запустити WAV із Windows Service під тестовим service account після холодного reboot та виміряти, що звук фізично доходить до підсилювача. Якщо драйвер/endpoint недоступний у Session 0, архітектуру відтворення потрібно переглянути окремим ADR; не вмикати інтерактивну службу як обхід. Документація Microsoft: [служби та інтерактивний сеанс](https://learn.microsoft.com/windows/win32/services/interactive-services), [Windows Audio Session API](https://learn.microsoft.com/windows/win32/coreaudio/wasapi).

### 13.2. Файл і формат

- Відтворювати тільки файл, знайдений через перевірений маніфест і локальний server-assigned `assetId`.
- Шлях канонізується відносно дозволеної директорії; відхиляти `..`, абсолютні шляхи від мережі, reparse points за межами каталогу й символічні посилання, що виходять із кореня.
- Перед відтворенням перевірити існування, розмір, дозволене розширення, SHA-256 та відповідність `manifestHash`.
- Перша версія обов’язково підтримує PCM WAV, інші формати приймати лише після узгодження декодера та тестів. Файл з мережі ніколи не передається прямо у плеєр до перевірки.
- Не кешувати нестиснені копії надовго; каталог має мати ліміт розміру, ACL служби й контрольоване видалення старих версій.

### 13.3. Обмеження відтворення

- Deadline дорівнює мінімуму з `issuedAtUtc + maxPlaybackDurationSeconds`, `expiresAtUtc` для ще не запущеної команди та локальної safety межі.
- Після старту звук може тривати лише до абсолютного deadline, незалежно від доступності Watcher.
- Watcher або WPF не можуть продовжити deadline прихованою повторною доставкою; нове продовження потребує нової валідної команди.
- Якщо потік зациклений, цикл контролює служба з монотонним таймером, а не позиція аудіофайлу чи мережевий heartbeat.
- Гучність задає налаштування обладнання/локального політики. Перша версія не змінює глобальну гучність Windows і не підвищує її автоматично до 100%.

### 13.4. Одночасні команди та пріоритет

DTO не передає числовий priority чи категорію сигналу. Тому вузол не визначає пріоритет за назвою `presetCode`, назвою файла або локальним списком.

Для першої версії дозволений лише один активний потік на вихід. Команда `stop` може зупинити тільки команду, зазначену в її `targetCommandId`; застаріла чи невідома ціль не зупиняє інший звук. Поведінка `start`, що надходить, поки вже грає інша команда, має бути погоджена з backend-контрактом до production. Рекомендація для першої версії: сервер формує явний `stop` старої команди, а потім новий `start` із більшим sequence. Не застосовувати неявне «останній звук завжди перемагає» до сигналів різних категорій.

## 14. Час та хвилина мовчання

- Усі часові мітки та таймери зберігати/передавати в UTC.
- Системний годинник Windows має синхронізуватися з NTP; панель попереджає, якщо Windows Time Service зупинена або розбіжність із сервером перевищила дозволені 120 секунд.
- Локальна зміна часу/часового поясу не змінює `expiresAtUtc` і playback deadline.
- Запуск хвилини мовчання о 09:00 Europe/Kyiv планує серверний scheduler; вузол отримує звичайну `start` команду і не створює локальний повторний запуск за власним годинником.
- Для системної команди зі строком до 09:01 вузол відхиляє повідомлення, яке прийшло після `expiresAtUtc`, навіть якщо транспорт відновився.
- Медіафайл і допустимий шлях його отримання мають бути присутні в перевіреному маніфесті; без цього команда завершується `preset_missing`/`manifest_mismatch` і не відтворюється.

## 15. Стан служби та відновлення

Використовувати явні стани служби:

```text
Starting → LoadingLocalState → CheckingCertificate → CheckingIdentity
         → Connecting → Streaming → Degraded → Reconnecting
         → Stopping → Stopped
```

Окремо від стану служби вести стан аудіо та синхронізації квитанцій. Не показувати «Працює», якщо WSS підключено, але identity не підтверджена або аудіовихід відсутній.

При відновленні після reboot:

1. Відкрити SQLite та виконати перевірку/міграції.
2. Перевести незавершене відтворення в `failed` із кодом `agent_restart`; не повторювати звук.
3. Підняти локальну чергу квитанцій.
4. Перевірити сертифікат, TLS сервер Watcher та `GET /device/identity`.
5. Якщо identity не збігається з локальним manifest scope, не відкривати WSS і показати помилку конфігурації.
6. Відновити WSS із backoff та передавати накопичені квитанції.
7. Виконувати тільки команди, строк яких не минув, а sequence не нижче локальної.

Падіння служби не може прибрати локальну БД чи квитанції. У разі пошкодження SQLite зберегти копію пошкодженого файла для адміністратора, перейти в fail-closed і не виконувати нові команди до відновлення локального стану.

## 16. Безпека Windows

- Службу запускати під окремим virtual service account або окремим локальним service account з мінімальними правами. `LocalSystem` дозволений лише після документованого тесту, який доводить потребу драйвера.
- Видати service SID і ACL тільки на `ProgramData\\KGTA\\Alert`, private key та Named Pipe.
- WPF працює без elevated privileges. Установник і ротацію сертифіката виконує адміністратор.
- Заборонити логування аудіоданих, токенів, приватного ключа, серійного номера секретного enrollment token, повних HTTP-заголовків і тексту винятків, які можуть містити секрет.
- Перевіряти TLS hostname і системний certificate chain. Не дозволяти downgrade на `http`/`ws`, self-signed серверний сертифікат без окремого тестового профілю або `ServerCertificateCustomValidationCallback = true`.
- Перевіряти розмір JSON, JSON depth, обмеження рядків і кількість полів. Невідомі поля ігноруються лише за сумісною політикою контракту; не робити polymorphic type activation.
- Аудіофайли вважати недовіреним вмістом до перевірки розміру, хешу та формату. Не відкривати файли з UNC-шляхів.
- Rate limit повторних TLS/HTTP-помилок на клієнті, щоб не створювати шторм запитів після втрати зв’язку.
- Установник не змінює системний firewall без показу конкретного правила й підтвердження адміністратора. Вхідні порти для Windows-вузла не потрібні.

## 17. Логи та діагностика

Записи служби мають містити час UTC, рівень, кореляційний `commandId` за наявності, назву підсистеми та стабільний diagnostic code. Наприклад:

```text
2026-11-05T09:00:00Z Information command.accepted commandId=... sequence=42
2026-11-05T09:00:01Z Information audio.playing commandId=... preset=air_raid
2026-11-05T09:15:01Z Warning audio.deadline_reached commandId=...
2026-11-05T09:15:02Z Information receipt.queued commandId=... state=completed
```

Не додавати payload команди чи квитанції повністю до журналу. Windows Event Log використовувати для запуску/зупинки служби, втрати сертифіката, пошкодження SQLite та критичних помилок; рутинні повідомлення зберігати у файлах з ротацією та лімітом розміру/строку.

Панель показує зрозуміле повідомлення й код, наприклад: «Не вдалося надіслати квитанцію. Вона збережена локально й буде надіслана після відновлення зв’язку. Код: `server_unavailable`.»

## 18. Інсталяція, оновлення та видалення

### Інсталяція

1. Перевірити Windows x64, потрібний runtime або використати self-contained publish.
2. Створити окремий каталог програми в `Program Files` та даних у `ProgramData`.
3. Створити service account/service SID і ACL на каталоги.
4. Зареєструвати сертифікат або показати чітку помилку про відсутність сертифіката; не генерувати прихований production identity.
5. Створити службу з автоматичним запуском після завантаження.
6. Запустити identity та аудіопробу в окремому режимі налаштування без екстреної команди.
7. Установити WPF-панель без прав адміністратора та зареєструвати її запуск лише для інтерактивного користувача.

### Оновлення

- Оновлення підписується й перевіряється до встановлення.
- Не оновлювати під час активного сигналу; відкласти та показати адміністратору.
- Перед оновленням зробити транзакційно-консистентну копію SQLite.
- Зберігати сумісність локальної схеми; міграції мають мати номер і перевірку rollback.
- У разі невдалого health check повернути попередній бінарний пакет без стирання квитанцій.

### Видалення

- Підтверджувати видалення локальної БД та аудіопакетів окремо від видалення програми.
- За замовчуванням зупинити службу й видалити бінарники, але зберегти дані та журнали до явної дії адміністратора.
- Видалення сертифіката/закритого ключа має бути окремим контрольованим кроком із записом результату в локальний журнал.

## 19. Тестування

### Unit-тести

- усі валідні/невалідні поля `CommandDispatch` для start/stop;
- UTC, deadline, межі sequence та гранична тривалість 1/900/901 секунд;
- формат manifest hash, preset code, UUID та diagnostic code;
- дубльований `commandId` із тим самим payload і з іншим payload;
- дубльований/нижчий sequence;
- переходи станів локальної машини та побудова квитанцій;
- backoff, jitter bounds, Retry-After та max retry delay;
- шлях traversal, UNC, reparse point, відсутній/пошкоджений файл;
- аварійне відновлення `accepted`/`playing` без повторного відтворення.

### Integration-тести

- міграція порожньої SQLite бази та оновлення з попередньої схеми;
- атомарність: crash/exception до commit не змінює sequence та outbox;
- crash після commit до запуску аудіо не запускає аудіо повторно після перезапуску;
- відправлення `accepted`, `playing`, завершального стану з незмінним event ID під час retry;
- серверні відповіді 202/200 duplicate/400/401/404/409/429/5xx;
- WSS trusted/untrusted server cert, відсутній/відкликаний client cert, невідповідний device identity;
- перепідключення, clean close, network reset, oversized frame, неправильний JSON;
- Named Pipe ACL і відмова сторонньому локальному користувачу;
- аудіопристрій відсутній, з’являється повторно, відключається під час відтворення;
- довгий файл зупиняється на жорсткому deadline незалежно від стану мережі.

### Апаратні та ручні перевірки

- cold boot без входу користувача;
- reboot під час активного тестового аудіо;
- вихід користувача та блокування екрана;
- перезапуск Windows Audio Service;
- вибраний endpoint від’єднали та повернули;
- відсутній доступ до сервера 30 хвилин, накопичення та подальша доставка квитанцій;
- недоступний DNS, неправильний системний час, прострочений клієнтський сертифікат;
- щонайменше 2 години безперервної роботи й перевірка пам’яті/логів.

## 20. Критерії приймання

Реалізація готова до тестового корпусу, якщо:

1. Служба встановлюється та запускається після cold boot без входу користувача.
2. Вузол не підключається до сервера без чинного довіреного mTLS сертифіката.
3. Сервер повертає identity, що збігається з вузлом і локацією його аудіопакета.
4. Команда з неправильним schema version, device/location ID, sequence, часом, строком або хешем не запускає аудіо.
5. Повторна доставка того самого `commandId` не запускає звук вдруге, навіть після аварійного перезапуску служби.
6. Запуск підтверджується різними станами `accepted` і `playing`; завершення передає фінальний стан.
7. Квитанція зберігається до відповіді сервера; повтор надсилається з тим самим event ID та незмінним payload.
8. Відтворення припиняється не пізніше заданого абсолютного deadline і межі 900 секунд, навіть без мережі.
9. Невідомий/відсутній аудіовихід показує діагностику й не переводить команду в `playing`.
10. Панель можна закрити без зупинки WebSocket, SQLite чи активної служби.
11. Після restart незавершений сигнал не запускається повторно автоматично.
12. Жоден лог, crash dump, конфігурація чи IPC-відповідь не містить приватного ключа, сертифікатного секрету або повного тіла команди.
13. Unit та integration набори запускаються локально й у CI; інтеграційні тести використовують окрему тимчасову БД, не production.
14. Серверний контракт підтримує потрібний перехід квитанції stop, а маніфест/файл доступні пристрою через mTLS до початку реального відтворення.

## 21. План робіт на іншому комп’ютері

### Етап 1. Перевірка аудіо на цільовому ПК

- Зафіксувати модель ПК, Windows edition/build, аудіоінтерфейс, підсилювач і кабельну схему.
- Перевірити, чи служба під окремим service account може відтворити тестовий PCM WAV у Session 0 після cold boot.
- Зробити інструментований прототип початку, завершення й примусової зупинки аудіо.
- Не переходити до UI, доки цей тест не пройде фізично через підсилювач корпусу.

### Етап 2. Локальний каркас

- Створити solution і проєкти service/core/infrastructure/tests.
- Додати конфігурацію, SQLite міграції, health state та Windows Service lifetime.
- Реалізувати безпечний Named Pipe й мінімальну статусну WPF-панель.

### Етап 3. Командний контракт

- Підключити спільний `Watcher.Contracts`.
- Реалізувати unit-тести validator і sequence/dedup до відкриття сокета.
- Реалізувати receipt outbox та HTTP mTLS-клієнт.

### Етап 4. Транспорт

- Перевірити mTLS identity на стенді.
- Реалізувати WSS reconnect та обмеження фрейму.
- Пройти end-to-end команди тестового звуку та квитанції на сервері.

### Етап 5. Медіапакети та stop

- Дочекатися затверджених серверних endpoint-ів маніфесту й файлів.
- Завершити серверний stop request/receipt contract.
- Додати підписане встановлення пакета, перевірки хешів, адресну зупинку та hardware tests.

### Етап 6. Тестовий корпус і rollout

- Встановити один вузол у тестовій локації.
- Перевірити журнал подій, аудіовихід, reconnect і відновлення після reboot.
- Перевірити rollback пакета й сертифіката.
- Після підписання приймального акту поступово додавати інші корпуси.

## 22. Вимоги до Git і PR

- Розробку вести у власній feature-гілці від актуального `develop`.
- Окремі коміти робити для каркаса solution, локальної схеми, транспорту, аудіопідсистеми, панелі, тестів та інсталятора; кожен коміт має бути логічним і з коротким людським повідомленням українською або російською.
- PR має описувати зміни, міграції SQLite, вимоги до сертифікатів, способи тестування та апаратні перевірки.
- Не включати до Git сертифікати, PFX, аудіофайли коледжу, реальні IP, локальну SQLite, дампи, логи або конфігурацію корпусу.
- Не зливати зміни з червоним CI або неперевіреним аудіо на цільовому ПК.
