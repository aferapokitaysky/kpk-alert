# Розгортання, домени та середовища

## Середовища

| Середовище | Призначення                       | Дані                                          |
| ---------- | --------------------------------- | --------------------------------------------- |
| Локальне   | розробка на комп’ютері розробника | вигадані дані, локальна база                  |
| Тестове    | перевірка інтеграцій і сценаріїв  | окремі облікові записи та тестові сертифікати |
| Робоче     | експлуатація закладом             | захищені секрети й обмежений доступ           |

Середовища не використовують спільні бази, сертифікати, cookie keys чи секрети.

## Доменна схема

Цільові назви треба підтвердити з адміністратором DNS. Як початкову схему пропонується:

| Ім’я                                                | Призначення                                 |
| --------------------------------------------------- | ------------------------------------------- |
| `notify.kgta.edu.ua`                                | панель оператора, HTTP API та SignalR Hub   |
| `journal.kgta.edu.ua` або фактичний домен Academica | система журналу та початкова точка переходу |

Для `notify` створюється DNS-запис на наявний reverse proxy. TLS-сертифікат має охоплювати точне ім’я. Не виставляти PostgreSQL назовні.

Перехід із журналу реалізується серверним обміном одноразового SSO-коду. Не задавати домен cookie `.kgta.edu.ua` і не передавати Google access token до PWA.

## Контейнери

Для розробки Docker Compose піднімає PostgreSQL, прив’язаний до loopback-інтерфейсу. Після появи застосунку додати контейнер Watcher і перевірку готовності. Edge Agent не запускається в Docker: його потрібно встановлювати як Windows-службу на фізичному вузлі біля аудіообладнання.

Робоче розгортання має містити щонайменше:

1. Reverse proxy з TLS і обмеженням заголовків.
2. Контейнер Watcher API, який слухає лише внутрішню мережу контейнерів.
3. PostgreSQL у приватній мережі з постійним томом.
4. Сховище Data Protection keys Watcher, що переживає перевипуск контейнера.
5. Окреме зашифроване сховище резервних копій із перевіркою процедури відновлення.

## Ключі cookie та перевірки стану

Compose зберігає кільце ASP.NET Data Protection у named volume `data-protection-keys`. Не видаляйте цей volume під час оновлення: без старих ключів чинні cookie перестануть читатися, а користувачам доведеться увійти повторно. Усі репліки одного середовища мають використовувати спільний том і `ApplicationName` `KGTA.Alert`.

У production ключі в цьому томі шифруються окремим сертифікатом PFX. Файл і пароль передаються платформою секретів, а не зберігаються в репозиторії чи `.env`. Для Compose змонтуйте PFX у контейнер лише для читання через локальний override-файл або секрети оркестратора, наприклад у `/run/secrets/data-protection.pfx`, і задайте:

```dotenv
ASPNETCORE_ENVIRONMENT=Production
DATAPROTECTION_CERTIFICATE_PATH=/run/secrets/data-protection.pfx
DATAPROTECTION_CERTIFICATE_PASSWORD=<пароль із сховища секретів>
```

Сертифікат має містити приватний ключ. Усі репліки повинні мати доступ до того самого сертифіката для читання раніше створених ключів. Під час ротації спершу розгорніть новий сертифікат разом зі старим на всіх репліках, потім перемкніть шифрування на новий і збережіть старий до завершення строку життя ключів. Розробницький Compose за замовчуванням використовує незашифроване локальне кільце; не переносіть його до production.

`GET /api/v1/health` і `/api/v1/health/live` перевіряють лише процес. Оркестратору слід призначити `GET /api/v1/health/ready` readiness-перевіркою: вона повертає `200` лише за доступної PostgreSQL, інакше — `503` без деталей підключення.
Порт бази даних не публікувати на зовнішній інтерфейс. Не зберігати production секрети в Compose-файлі чи образі контейнера.

## Зовнішні джерела тривог

Для alerts.in.ua задайте токен через secret store як `ALERTS_IN_UA_TOKEN` або конфігураційне значення `AlertSources:AlertsInUa:Token`. Не передавайте токен у клієнтському bundle, URL, журнали чи відповіді API.

Кеш і блокування запитів `GET /api/v1/alert-sources/status` поки існують лише в пам'яті процесу. До появи спільної координації опитування розгорніть Watcher в одній репліці: кілька реплік можуть окремо звертатися до upstream і перевищити їхній м'який ліміт частоти. Горизонтальне масштабування цього сервісу потребує спільного кешу та розподіленого блокування або централізованого опитувача.

Для UkraineAlarm задайте API-токен у secret store як `UkraineAlarm:Token` (`UkraineAlarm__Token`) і зовнішній HTTPS origin як `UkraineAlarm:PublicBaseUrl` (`UkraineAlarm__PublicBaseUrl`). Origin має бути без шляху, облікових даних, query та fragment. Інтервал фонового опитування налаштовується через `UkraineAlarm:PollInterval` (`UkraineAlarm__PollInterval`, формат `00:01:00`, типово одна хвилина); значення менше однієї хвилини відхиляються, щоб обмежити навантаження на upstream. З’єднання з API оновлюються кожні п’ять хвилин, щоб клієнт підхоплював зміну DNS-адреси сервісу навіть за довготривалого singleton-клієнта. Токен надсилається лише у `Authorization` і не має потрапляти до журналів чи URL.

UkraineAlarm callback-адреса має вигляд `https://<публічний-origin>/api/v1/alert-sources/ukrainealarm/webhook`. Застосунок не створює й не змінює реєстрацію під час запуску. Початковий стан у базі — `unknown`: глобальний адміністратор має звірити callback у кабінеті провайдера, щоб не створити дублікат. Подальші зміни запускаються через `POST /api/v1/admin/integrations/ukrainealarm/webhook-operations` із cookie-сесією, CSRF та `Idempotency-Key`; URL береться лише з перевіреного `UkraineAlarm:PublicBaseUrl`. Якщо операція `Unknown`, звірте реєстрацію в UkraineAlarm і зафіксуйте результат через endpoint `resolve`. Для завислої `Pending`/`Running` операції спочатку зупиніть усі екземпляри API, а потім виконайте `ops/recover-ukrainealarm-webhook-operation.sql` із UUID операції та активного глобального адміністратора: `PGSERVICEFILE=/etc/kgta-alert/pg_service.conf PGPASSFILE=/run/secrets/postgres-pgpass psql "service=kgta-alert-recovery" -v operation_id='UUID_ОПЕРАЦІЇ' -v actor_id='UUID_АДМІНІСТРАТОРА' -f ops/recover-ukrainealarm-webhook-operation.sql`. У service file задайте адресу й назву бази без пароля; пароль надайте через `PGPASSFILE` із правами доступу лише власнику. Скрипт атомарно переводить стан у `Unknown` і додає запис аудиту від активного глобального адміністратора. Продовжуйте лише після результату `INSERT 0 1`; після цього запустіть API, перевірте стан у кабінеті провайдера та завершіть `resolve`. Не передавайте пароль БД у DSN чи аргументах процесу й не зберігайте його в shell history. Не змінюйте ці записи довільними SQL-командами. Зміни, зроблені поза Watcher, відображайте через `state/reconcile`. Токен залишається тільки в secret store і не вставляється до командного рядка, журналів чи запитів браузера.

NEPTUN за замовчуванням читається через REST. Для одного екземпляра можна ввімкнути потік `AlertSources:Neptun:Realtime:Enabled=true` (`AlertSources__Neptun__Realtime__Enabled=true`); тайм-аут heartbeat, інтервал REST fallback, затримки повторного підключення й ліміт повідомлення налаштовуються під `AlertSources:Neptun:Realtime`. Монітор відкриває одне WSS-з’єднання та використовує REST для початкового стану й відновлення. Кілька реплік створять незалежні з’єднання й локальні знімки, тому режим realtime підтримується лише в одній репліці.

Webhook endpoint UkraineAlarm публічний, бо опублікований SDK не описує підпису чи способу передати додатковий заголовок. Застосунок обмежує тіло до 8 KiB, кількість запитів — до 10 на хвилину з однієї IP-адреси, а сигнал повторної перевірки — до одного на 5 секунд у межах процесу. Callback використовується лише як недовірений wake-up; джерело істини — авторизовані відповіді UkraineAlarm API. Фоновий worker зареєстрований у `AddAlertSources`, приймає callback-сигнал для позачергової перевірки та зберігає мінімальну хвилину між upstream-опитуваннями. На reverse proxy задайте додатковий ліміт частоти для `/api/v1/alert-sources/ukrainealarm/webhook` і не записуйте тіло запиту в журнали. Метрика `ukrainealarm.webhook.requests` рахує лише результат callback без IP чи payload. Поки немає спільного кешу, блокування й ліміту між репліками, запускайте одну репліку Watcher.

WebSocket-присутність пристроїв є спільною для реплік і зберігається у `device_sessions`. Сервер надсилає WebSocket keep-alive кожні 15 секунд, очікує pong до 30 секунд і оновлює heartbeat сеансу кожні 5 секунд. Панелі вважають вузол підключеним протягом 20 секунд від останнього heartbeat. Під час reconnect сервер блокує рядок пристрою PostgreSQL, завершує попередні сеанси й лише потім створює новий. Для коректної роботи кількох реплік усі вони мають використовувати одну PostgreSQL базу.

## Канал пристроїв mTLS

Панель оператора та пристрої використовують різні точки входу. Reverse proxy завершує публічний TLS для браузерного трафіку. Пристрої підключаються напряму до окремої HTTPS-точки Kestrel з обов’язковим клієнтським сертифікатом; не завершуйте TLS пристроїв на проксі, який не передає довірену ідентичність клієнта. Не передавайте відбиток сертифіката через HTTP-заголовок. У production застосунок не запуститься, якщо mTLS listener не ввімкнено або він налаштований на іншому порту чи без `RequireCertificate`.

Застосунок приймає `X-Forwarded-For`, `X-Forwarded-Proto` та `X-Forwarded-Host` лише від адрес із `ReverseProxy:KnownProxies`; production стартує тільки з непорожнім allowlist і `ReverseProxy:HttpsPort`. Для контейнерного розгортання задайте, наприклад, `ReverseProxy__KnownProxies__0=10.20.0.10` і `ReverseProxy__HttpsPort=443`, замінивши адресу на стабільну внутрішню адресу TLS-proxy. Проксі має видаляти надіслані клієнтом `X-Forwarded-*` заголовки й записувати власні значення. Middleware обробляє один довірений proxy-hop. `X-Forwarded-Proto` зберігає зовнішню HTTPS-схему для OAuth та запобігає перенаправленню браузерного трафіку на пристроєвий mTLS-порт. Не додавайте адресу пристроя або загальнодоступну підмережу до allowlist.

Локальний Compose за замовчуванням піднімає лише HTTP listener. Для окремої mTLS-точки використовуйте overlay `compose.mtls.yaml`; він додає HTTPS listener на порті `8443`, режим `RequireCertificate` і монтує серверний сертифікат та кореневий CA лише для читання. Приклад запуску:

```bash
DEVICE_SERVER_CERTIFICATE_FILE=/srv/secrets/device-server.pfx \
DEVICE_SERVER_CERTIFICATE_PASSWORD_FILE=/srv/secrets/device-server-password \
DEVICE_CLIENT_CA_CERTIFICATE_FILE=/srv/secrets/device-root-ca.crt \
DEVICE_MTLS_BIND_ADDRESS=10.20.0.5 \
docker compose -f compose.yaml -f compose.mtls.yaml up -d
```

Overlay передає порти й шляхи до файлів секретів. Застосунок явно відкриває HTTP listener для reverse proxy та окремий HTTPS listener для пристроїв з `ClientCertificateMode.RequireCertificate`; налаштування перевіряються на старті. Порт `8443` прив’язується до приватної адреси вузла; не відкривайте його через загальнодоступний reverse proxy. Серверний PFX має відповідати адресу пристроїв і містити приватний ключ. Пароль PFX, PFX і сертифікат CA монтуються лише для читання. CA — самопідписаний корінь довіри для клієнтських сертифікатів; застосунок використовує лише його для перевірки ланцюжка. Вузол має надавати доступ до CRL, зазначеного в ланцюжку, для перевірки відкликання CA.

На кожному вузлі має бути довіра до сертифіката сервера: встановіть кореневий сертифікат його CA у сховище довіри ОС або використайте сертифікат від уже довіреного CA. Клієнтський сертифікат вузла має містити призначення `clientAuth` і бути виданий CA, змонтованим до Watcher.

Контейнер працює від non-root `APP_UID` (у базовому ASP.NET образі це UID `1654`). Під час bind mount права перевіряються за числовими UID/GID: PFX і файл пароля мають читатися цим UID, але не бути доступними всім користувачам. Для звичайного rootful Docker підготуйте файли так:

```bash
sudo chown 1654:1654 /srv/secrets/device-server.pfx /srv/secrets/device-server-password /srv/secrets/device-root-ca.crt
sudo chmod 0400 /srv/secrets/device-server.pfx /srv/secrets/device-server-password /srv/secrets/device-root-ca.crt
```

Не використовуйте `chmod 0444` для PFX чи його пароля. У rootless Docker або з user namespace зіставте UID/GID контейнера з UID/GID хоста та надайте читання лише цьому власнику чи окремій групі; не розширюйте права до `other`.

Вмикайте канал послідовно: змонтуйте секрети, перевірте адресу сертифіката сервера й доступність CRL з контейнера, потім додайте firewall allow rule лише для однієї тестової IP-адреси вузла до TCP `8443`. Після цього запустіть Compose з overlay і перевірте TLS handshake та `GET /api/v1/device/identity` із цього вузла. Лише після успішної перевірки розширте allow rule на затверджений перелік адрес/підмереж вузлів; решта мережі має залишитися заблокованою. Якщо перевірка не пройшла, приберіть тестове правило та overlay. Production без listener-а не стартує.

**Production onboarding пристроїв поки недоступний.** API перевіряє SHA-256 відбиток із заздалегідь зареєстрованого запису `devices`, але в репозиторії ще немає затвердженого процесу випуску сертифіката, перевірки особи вузла та безпечної реєстрації/ротації відбитка. Не створюйте production-сертифікати й не додавайте записи пристроїв вручну в базу. До затвердження такого процесу використовуйте канал лише в тестовому середовищі з окремими тестовими сертифікатами.

Помилка TLS handshake або відсутність HTTP-відповіді означає, що з’єднання відхилено до маршрутизації API: перевірте адресу/порт, серверний сертифікат, наявність клієнтського сертифіката, довіру до CA, строк чинності та доступність CRL. Якщо TLS встановлено, але endpoint повертає `401` чи `403`, перевірте SHA-256 відбиток сертифіката в записі пристрою, `RevokedAtUtc` і активність локації. Клієнтські `deviceId` та `locationId` для діагностики або автентифікації не передаються.

Для кожної автентифікації Watcher звіряє відбиток із записом пристрою та перевіряє, що пристрій не відкликаний, його корпус активний, а сертифікат перебуває в межах строку чинності. Перевірка реєстру виконується без кешування, тому відкликання застосовується до наступного запиту пристрою. Ротацію виконуйте після безпечного випуску нового сертифіката та оновлення запису пристрою.

## Конфігурація

Налаштування передаються через змінні середовища або secret store системи розгортання. `.env.example` містить тільки локальні приклади. Робочі значення ніколи не додаються в Git.

Перед запуском Watcher перевіряє наявність обов’язкових параметрів: рядка підключення до бази, шляхів/ідентифікаторів сховища ключів, параметрів SSO, зовнішнього джерела та політики вузлів. Не виводити значення секретів у повідомлення помилок.

Worker матеріалізації outbox увімкнений за замовчуванням. Налаштуйте його змінними середовища `CommandOutboxWorker__Enabled`, `CommandOutboxWorker__PollInterval` і `CommandOutboxWorker__BatchSize` (формат інтервалу — `00:00:10`). Допустимі значення: інтервал від 100 мс до 5 хвилин, пакет від 1 до 500 подій; некоректна конфігурація зупиняє застосунок під час запуску. Встановіть `CommandOutboxWorker__Enabled=false`, якщо потрібно тимчасово призупинити створення delivery-записів; команди й outbox при цьому продовжують зберігатися, а очікувані події обробляться після повторного ввімкнення.

Transport команд пристроям також увімкнений за замовчуванням. Налаштуйте `DeviceCommandTransport__Enabled`, `DeviceCommandTransport__PollInterval`, `DeviceCommandTransport__SendTimeout`, `DeviceCommandTransport__AcknowledgementTimeout`, `DeviceCommandTransport__InitialRetryDelay`, `DeviceCommandTransport__MaximumRetryDelay` і `DeviceCommandTransport__BatchSize`. Тайм-аут запису WebSocket за замовчуванням — 5 секунд, допустимо від 1 до 15 секунд; він обмежує тривалість блокування пристрою під час передачі команди. Тайм-аут квитанції за замовчуванням — 10 секунд, допустимо до 60 секунд; він визначає, скільки чекати на ACK перед повтором. Типовий цикл — 250 мс, backoff повторів — від 1 до 15 секунд, пакет — до 50 доставок. Worker працює лише з WebSocket-сесіями поточного процесу та зберігає стан доставки в PostgreSQL. Пристрої мають підключатися до окремого device listener із mTLS; проксі повинен передавати WebSocket Upgrade на цей порт, а не на публічний вебпорт. Якщо потрібно призупинити доставку, встановіть `DeviceCommandTransport__Enabled=false`; записи залишаться в базі й не будуть видалені.

## Перевірка перед публікацією

- зібрати та підписати контейнер із зафіксованою версією базового образу;
- застосувати сумісні міграції бази й перевірити статус здоров’я сервісу;
- перевірити TLS, callback URL, SSO та відмову в доступі неавторизованого користувача;
- перевірити підключення вузла, доставку тестової команди й отримання ACK;
- перевірити, що журнали не містять секретів;
- зафіксувати версію й мати перевірений план відновлення.

Порядок розгортання й відновлення — у [операційних інструкціях](runbooks/README.md).
