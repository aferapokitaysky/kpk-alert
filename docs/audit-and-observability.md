# Журнал аудиту та технічна діагностика

## Призначення

Система має відповідати на два різні запитання:

- хто, що і коли зробив, та який результат зафіксувала система;
- чому сервіс або окремий інтеграційний компонент працює неправильно.

Для першого використовується незмінюваний штатними операціями журнал `audit_events` і пов’язані з ним записи команд, доставок та квитанцій у PostgreSQL. Для другого — структуровані журнали `ILogger`. Метрики призначені для частих однотипних спостережень, наприклад heartbeat або циклів опитування. Жоден з цих каналів не є заміною іншому.

## Цільова модель подій аудиту

Наведений нижче перелік є цільовою моделлю аудиту, а не твердженням, що всі ці події вже зберігаються. Фактичне покриття й відомі прогалини описані в розділі «Поточний стан і наступні кроки». Аудит призначений для значущих переходів стану та дій людей, а не для кожного HTTP-запиту чи heartbeat. Коли стан і аудит належать одній операції, їх потрібно зберігати в одній транзакції.

`ActorType` відрізняє `user`, `system`, `device` та зовнішню інтеграцію; `ActorId` вказується, якщо для суб’єкта є локальний ідентифікатор. Для системної команди ініціатор не підміняється користувачем. Час зберігається в UTC. Для події вузла зберігаються окремо час, заявлений вузлом, і серверний `ReceivedAtUtc`; різницю годинників можна оцінити без втрати фактичного часу отримання.

## Життєвий цикл команди

Для розбору інциденту події пов’язуються за `commandId`; події доставки додатково містять `deviceId` і `locationId`, а повторна доставка — номер спроби. Системи журналювання додають `TraceId` для мережевого запиту, коли він існує.

1. **Створено** — сервер атомарно зберіг намір, цілі, outbox і аудит. HTTP `202 Accepted` означає лише прийняття запиту сервером.
2. **Спроба надсилання** — сервер позначив доставку `InFlight`, збільшив лічильник і записав `alert_command.delivery_attempt_started` до виклику WebSocket. Це підтверджує лише початок спроби; стан не доводить, що байти були передані або отримані вузлом. В інтерфейсі цей стан показується як «Надсилається».
3. **Результат запису у WebSocket** — `alert_command.delivery_write_result` має один із результатів. `completed` означає, що запис у WebSocket завершився, але не підтверджує отримання вузлом. `not_started` означає, що запис не почався, наприклад через недоступність вузла або зміну сесії до передачі. `indeterminate` означає, що під час уже розпочатого запису сталася помилка WebSocket або тайм-аут чи виклик скасовано через зупинку сервісу; часткова передача можлива, тож стан перевіряють за квитанцією вузла.
4. **Прийнято вузлом** — вузол зберіг команду й надіслав квитанцію `Accepted`. Це окрема подія після спроби запису.
5. **Програмне відтворення запущене** — вузол надіслав квитанцію `Playing` після виклику аудіовиходу й збереження локального стану. Це звіт Edge Agent про запуск програмного шляху відтворення; система не має акустичного loopback або апаратного датчика, тому квитанція не доводить, що звук фізично вийшов із динаміка чи був чутний.
6. **Завершено** — вузол повідомив `Completed`, `Stopped` або термінальний результат відмови. Для команди з кількома вузлами результат показується окремо на кожний вузол; агрегат не приховує часткову невдачу.

Якщо процес завершується аварійно після `delivery_attempt_started`, але до збереження `delivery_write_result`, сервер під час повторної спроби або завершення строку дії записує `indeterminate` із кодом `previous_attempt_result_missing` для попереднього номера спроби. Це не доводить отримання команди. Повтор використовує той самий ID команди, а вузол дедуплікує його; фактичний результат звіряють із квитанцією.

`Expired` потребує окремої перевірки: сервер може позначити доставку простроченою після завершення строку команди без квитанції від вузла. Стан `Expired` у `command_deliveries` сам по собі не доводить, що вузол отримав команду й повідомив про завершення строку. Для цього потрібна пов’язана квитанція у `command_receipts`.

`AlertLevel` походить із нормалізованого спостереження джерела тривоги. `PresetCode` вказує обраний звуковий сценарій. `SoundPreset.Priority` використовується лише для сортування сценаріїв у UI й не є частиною контракту відтворення. Жодне з цих значень не є акустичною гучністю й не доводить, що звук фізично вийшов із динаміка. Керування фізичною гучністю потребує окремої узгодженої властивості та контракту.

Ручні команди та запуск хвилини мовчання зберігають актора/джерело команди й обраний `PresetCode`. Автоматична команда зберігає `AlertLevel` разом із джерелом, областю/обсягом і часом спостереження; `PresetCode` показує обраний для неї сценарій.

## Технічні журнали та навантаження

- Використовувати структуровані поля й сталі шаблони `ILogger`; не будувати повідомлення конкатенацією даних користувача.
- Записувати старт і завершення важливих фонових операцій, помилки провайдерів, помилки БД/транспорту, тайм-аути й причини повтору. Успішний частий polling і heartbeat агрегувати метриками або писати на `Debug`, а не створювати необмежений потік `Information`.
- Для фонового циклу логувати підсумок пакета (кількість, тривалість, результат), а не кожну порожню перевірку черги.
- Подію аудиту записувати один раз на суттєвий перехід стану. Повторна квитанція дедуплікується; вона не створює другий логічний результат.
- Зберігати `commandId`, `deviceId`, `locationId`, код події, час і результат — це дає змогу дослідити інцидент без повного payload.
- Health check логувати лише при зміні стану або помилці; регулярні успішні перевірки не мають засмічувати журнали.

## Дані, які заборонено записувати

Не записувати паролі, OAuth/API токени, cookie, CSRF-токени, приватні ключі чи паролі сертифікатів, одноразові коди входу, повні заголовки запитів, тіла callback/відповідей провайдерів, сирі аудіодані, stack trace у відповідь користувачеві або зайві персональні дані. У повідомленнях про відмову використовувати allowlist-коди; не переносити текст винятку чи дані від зовнішнього сервісу в аудитовий payload.

IP-адреса, email і зовнішній subject не додаються до технічного журналу лише «про всяк випадок». Якщо розслідуванню потрібен конкретний персональний атрибут, його мету, доступ і строк зберігання слід затвердити окремо.

## Доступ, цілісність і зберігання

Читати журнал аудиту можуть лише глобальні `admin` та `auditor`; перевірка виконується сервером для кожного запиту. Записи аудиту не редагуються або видаляються звичайною функцією застосунку. Резервна копія PostgreSQL повинна охоплювати `audit_events`, команди, доставки й квитанції як один узгоджений знімок.

Застосунок не встановлює автоматичне видалення аудиту. Точний строк зберігання, архівацію, доступ операторів Coolify до runtime logs та ротацію Docker-журналів потрібно затвердити з коледжем до production; не додавати purge job без цього рішення. Секрети не можна передавати до зовнішнього сервісу логування без окремого погодження та перевірки його регіону зберігання й контролю доступу.

## Поточний стан і наступні кроки

У БД є `audit_events`, стани `command_deliveries` і дедупліковані `command_receipts`. Поточна реалізація аудиту фіксує `alert_command.delivery_attempt_started` перед socket-записом та `alert_command.delivery_write_result` після завершення запису або обробки результату виклику з outcome `completed`, `not_started` чи `indeterminate`. `completed` свідчить лише про завершення WebSocket-запису, не про отримання команди вузлом; для цього потрібна квитанція. `not_started` означає, що socket-запис не почався. `indeterminate` виставляється, якщо під час уже розпочатого запису сталася помилка WebSocket або тайм-аут чи виклик скасовано через зупинку сервісу, коли передавання могло бути частковим. Якщо процес падає до збереження події результату, сервер визначає це за відсутнім результатом останньої спроби, записує `indeterminate` із кодом `previous_attempt_result_missing` перед повтором або завершенням доставки й надалі звіряє результат із квитанціями. `command_deliveries` окремо зберігає агрегатний `AttemptCount`, останню спробу, результат останнього socket-запису й наступний час повтору; цей агрегат не замінює подій на кожну спробу. Під час міграції відомі результати останньої спроби відновлюються з наявного аудиту. Перед production потрібно перевірити повноту переходів інших підсистем і узгоджену політику зберігання. `AlertLevel` від API слід зберігати окремо від обраного `PresetCode`. Квитанція `Playing` підтверджує лише запуск програмного шляху відтворення, а не звук із динаміка. Runtime logs і метрики не замінюють durable audit.

Подія `integration.alert_source.state_changed` створюється під час першого спостереження та зміни нормалізованих `Level`, `AlertLevel`, `Freshness`, коду помилки або last-known стану для конкретних `Source`, `Scope` і `ScopeId`. Зміна лише `CheckedAtUtc` не створює аудитової події; актуальний час перевірки зберігається в стані джерела. Спостереження з часом перевірки старше за збережений стан ігноруються. Запис серіалізований у PostgreSQL, щоб кілька екземплярів API не дублювали один перехід. Сирий payload і URL атрибуції джерела не записуються.

Вхідний callback UkraineAlarm не є командою тривоги: він лише просить сервер позачергово оновити стан через API провайдера. Лічильник `ukrainealarm.webhook.requests` рахує `accepted`, `rate_limited` і `too_large` без адреси та вмісту запиту. Структурований запис журналу створюється, коли callback поставив новий сигнал оновлення; callback, об’єднані з уже очікуваним сигналом, не створюють повторних записів.

Подія `automatic_alert.held` містить `DecisionCode` і масив `Observations` розміром до 24 елементів. Для кожного елемента записуються лише нормалізовані `Source`, `Scope`, `ScopeId`, `Level`, `AlertLevel`, `Freshness`, `CheckedAtUtc` і `DataUpdatedAtUtc`; `ObservationsTruncated` вказує, чи було обрізано перелік. Сирі відповіді провайдерів до аудиту не копіюються.
