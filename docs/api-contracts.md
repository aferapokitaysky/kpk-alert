# Контракти API та доставки команд

## Загальні вимоги

- HTTP API має префікс `/api/v1`; несумісні зміни виносяться в нову версію.
- Браузерні запити, що змінюють стан, захищаються anti-forgery токеном.
- Зареєстровані вузли взаємодіють із Watcher через HTTPS REST API; окремий Kestrel listener обов’язково вимагає клієнтський TLS-сертифікат (mTLS).
- Повтор того самого запиту з тим самим `Idempotency-Key` повертає попередній результат; якщо тіло відрізняється, API повертає `409 Conflict`.
- Дата й час передаються у форматі RFC 3339 із часовим поясом UTC.

Маршрути входу: `GET /api/v1/auth/login` (перехід до Google OAuth), `GET /api/v1/auth/csrf-token` (видача парного request token і cookie), `GET /api/v1/auth/session` (поточний стан сесії, глобальні ролі та можливості UI) і `POST /api/v1/auth/logout` (завершення локальної сесії). Session endpoint повертає лише `authenticated`, allowlist глобальних ролей та `capabilities.canOperate` / `capabilities.canViewAudit`; він не розкриває email, Google subject, токени чи локальні призначення. Локальні ролі дають змогу відкрити пульт, але не надають глобального доступу до журналу аудиту. Backend окремо перевіряє права для кожної локації та endpoint аудиту. Для logout та створення команди браузер передає request token у заголовку `X-CSRF-TOKEN`; cookie `__Host-KgtaAlert.AntiForgery` має прапорці Secure, HttpOnly і SameSite=Strict. Google OAuth увімкнений лише за наявності `Authentication:Google:Enabled`, Client ID та Client Secret. Увійти можуть лише активні користувачі, яких адміністратор попередньо зареєстрував у базі за зовнішнім Google subject.

## Керування обліковими записами

Маршрути `/api/v1/admin/users` доступні лише глобальним адміністраторам; сервер перевіряє чинне призначення ролі в базі даних під час кожного запиту. Список приймає `page` (від 1), `pageSize` (1–100, типово 25) і необов'язковий пошук `search` за email (до 100 символів). Відповідь містить лише ID, email, активність і призначені ролі з назвами локацій. Відповіді не кешуються.

Каталог повертає наявні ролі `admin`, `auditor`, `notificator` і `sound_engineer`. `admin` та `auditor` призначаються лише глобально; операторські ролі можуть бути глобальними або обмеженими активною локацією. Створення облікових записів і запрошення не входять до цих маршрутів: користувач має бути попередньо зареєстрований за зовнішнім Google subject.

Для PATCH, POST і DELETE обов'язкові cookie-сесія та `X-CSRF-TOKEN`. Повторне призначення тієї самої ролі в тій самій області дії повертає наявне призначення без другого запису аудиту. Зміна активності, призначення і відкликання ролі записуються в аудит разом зі зміною даних. Облікові записи не видаляються фізично. Адміністратор не може деактивувати себе чи зняти з себе глобальну роль `admin`; також система не дозволяє деактивувати або позбавити ролі останнього активного глобального адміністратора. Мутації серіалізуються транзакційним advisory-блокуванням PostgreSQL, щоб паралельні запити не обійшли цю гарантію.

`GET /api/v1/locations` повертає лише активні корпуси, доступні ролі користувача. Глобальний адміністратор або оператор бачить усі активні корпуси; локальне призначення ролі відкриває лише закріплені корпуси.

`GET /api/v1/presets` повертає лише опубліковані сценарії для адміністратора або оператора з глобальною чи локальною роллю. Пульт будує кнопки з цієї відповіді; неопубліковані або відсутні в базі сценарії не відображаються. Endpoint наразі підтримує лише запуск звукового сценарію, а окрема дія «Відбій» потребує власного контракту та прив’язки до активної події.

`GET /api/v1/audit-events` доступний користувачам із глобальною роллю `auditor` або `admin`; локальне призначення цих ролей доступу не надає. Параметри `page` (від 1, типово 1) та `pageSize` (1–100, типово 50) керують посторінковою видачею; `eventType` необов’язково залишає події одного точного типу, а `actorId` фільтрує за UUID актора. `fromUtc` і `toUtc` задають обов’язкову пару меж RFC 3339 у UTC: початок включено, кінець виключено, максимальна тривалість — 90 днів. Некоректні межі, непарний параметр або довший діапазон повертають `400`. Відповідь містить `items`, `page`, `pageSize` і `totalCount`; кожна подія повертає ID, тип, тип і ID актора, час UTC та JSON-поле `payload`. Події впорядковані від нових до старих; за однакового часу порядок задає ID. Відповідь має `Cache-Control: no-store`. API не приймає довільний SQL-фільтр і не повертає email, зовнішній subject, IP-адреси чи токени.

`GET /api/v1/minute-of-silence/status/today` доступний лише користувачам із глобальною роллю `admin` або `auditor`. API визначає поточну дату в `Europe/Kyiv`, повертає очікуваний час 09:00 у UTC та збережений результат: `outcome` дорівнює `queued` або `skipped`, а для пропущеного вікна запуску `skipReason` містить `missed_window`. Інша причина пропуску — `outside_execution_window`. Якщо запис за поточну дату ще не створено, поля результату мають значення `null`. Відповідь не кешується; перевірка ролі читає актуальне призначення з бази даних.

`GET /api/v1/minute-of-silence/history?from=YYYY-MM-DD&to=YYYY-MM-DD&page=1&pageSize=25` доступний лише користувачам із глобальною роллю `admin` або `auditor`. Дати `from` і `to` обов’язкові та включаються до вибірки; період може охоплювати не більше 90 календарних днів і має завершуватися сьогодні або раніше за `Europe/Kyiv`. `page` починається з 1, а `pageSize` має бути в межах 1–100. Записи читаються лише з `minute_of_silence_occurrences`, сортуються за `runDate` від найновішого до найстарішого та повертають `runDate`, збережені `outcome` і `skipReason` та `processedAtUtc`. Час у відповіді задано UTC; інтерфейс показує його в `Europe/Kyiv`. API не перераховує минулі результати й не додає стан доставки чи відтворення. Невалідний діапазон або пагінація повертають `400`; відповідь не кешується.

`GET /api/v1/alert-sources/status` повертає інформаційні спостереження від UkraineAlarm, NEPTUN і alerts.in.ua окремо для Полтавської області, Кременчуцького району й Кременчуцької громади. Endpoint не вимагає сесії, не запускає команд і не передає браузеру токени джерел. `authoritativeObservation` вибирається за пріоритетом UkraineAlarm → NEPTUN → alerts.in.ua; нижче джерело використовується лише за відсутності свіжого відомого спостереження від попереднього. Розбіжність актуальних джерел відображається як `conflict`, але не змінює це поле. UkraineAlarm повідомляє лише `active`/`inactive`, без вигаданого рівня кольору. alerts.in.ua має точні UID області `19` і громади `1088`; код `N` консервативно відображається як `unknown`, бо документація endpoint описує його як відсутність інформації. NEPTUN надає область і район; адаптер зіставляє записи за стабільними ключами `poltavska` та `poltavska:kremenchutskyi`, а районний статус не використовується як статус громади. Ключ є основним ідентифікатором, тому зміна підпису не змінює відповідний статус; знайома назва з неочікуваним ключем сигналізує невідомий контракт. Дубльований ключ або запис некоректного формату дає `unknown`, а не підтверджену відсутність тривоги. Час `since` у NEPTUN означає початок події, тому його не передають як час оновлення даних. Поле `level` може бути `active`, `inactive`, `partial`, `unknown` або `conflict`; `freshness` — `fresh`, `stale` або `unknown`. Для автоматизованого споживача `authoritativeObservation` вказує вибране актуальне спостереження, а перелік `observations` зберігає окремі відповіді джерел. Червоний і жовтий рівні передаються лише коли їх повідомило джерело. Помилка, обмеження частоти чи застаріла відповідь не означають відсутність тривоги; неочікуваний виняток одного провайдера лишає його стан невідомим і не перериває відповідь іншого. Токени джерел налаштовуються тільки на сервері; їх не можна записувати до репозиторію чи журналу. Кожна картка інтерфейсу містить посилання на джерело.

Автоматичне створення команд керується серверними параметрами `AlertSources:AutomaticDispatch:Enabled`, `PresetCode` і `PollInterval`; у прикладі конфігурації функція вимкнена. Після явного ввімкнення policy створює одну системну команду `start` на підтверджений епізод тривоги та команду `stop` лише після свіжого географічно достатнього підтвердження відбою. Стан епізоду блокується `FOR UPDATE`, а епізод, команда, цілі, послідовності, outbox та аудит фіксуються в одній транзакції. Повторні спостереження й паралельні репліки не створюють повторну команду. Якщо пресет не опублікований, має некоректний manifest або немає активних корпусів, запуск утримується. Статус доступний лише глобальним `admin` і `auditor`, не кешується. Створена команда не підтверджує відтворення звуку; підтвердження надходить окремими квитанціями доставки.

### UkraineAlarm WebHook і опитування

Серверний клієнт UkraineAlarm API v3 передає токен лише в заголовку `Authorization`; токен не додається до URL, тіла запиту, журналів чи відповіді браузеру. Реєстрація та оновлення WebHook використовують `POST` і `PATCH /api/v3/webhook` з моделлю `{ "webHookUrl": "https://..." }`. Публічна адреса Watcher має бути задана через `UkraineAlarm:PublicBaseUrl` і повинна бути HTTPS origin без шляху, query, fragment чи userinfo; клієнт формує з неї callback URL. Токен задається окремо через `UkraineAlarm:Token`.

Керування реєстрацією доступне лише користувачам із глобальною роллю `admin`; призначення ролі перевіряється за базою для кожного запиту. Зміни потребують cookie-сесії, CSRF-токена й UUID у заголовку `Idempotency-Key`. `POST /api/v1/admin/integrations/ukrainealarm/webhook-operations` приймає `{ "action": "register" }` або `{ "action": "update" }` і повертає `202 Accepted` з `id`, станом операції та серверною callback-адресою. Повтор того самого ключа тим самим адміністратором і з тією самою дією повертає збережений результат, не викликаючи UkraineAlarm повторно; інша дія або актор для цього ключа дають `409`. `GET /api/v1/admin/integrations/ukrainealarm/webhook-operations/state` повертає стан реєстрації та `activeOperation` для найдавнішої незавершеної операції `Pending`, `Running` або `Unknown` (або `null`, якщо такої немає). Це дає змогу відновити операцію після перезавантаження панелі. Стан окремої операції також повертає `GET /api/v1/admin/integrations/ukrainealarm/webhook-operations/{operationId}`.

Початковий стан реєстрації — `unknown`. Перед першою дією звірте webhook у кабінеті UkraineAlarm і передайте результат через `POST /api/v1/admin/integrations/ukrainealarm/webhook-operations/state/reconcile` з `{ "confirmed": true, "isRegistered": true|false }`. `register` доступний лише за підтвердженого стану `not_registered`; `update` — лише коли стан відомий як `registered`. Після відповіді `2xx` провайдера операція стає `Succeeded`. Відповідь `4xx` дає `Rejected`; транспортна помилка, скасування, `5xx` або збій після відправлення дають `Unknown`, бо зовнішній ефект не можна виключити. `Pending`, `Running` і `Unknown` блокують нові зміни. Через `resolve` дозволено підтвердити лише `Unknown`: для `Pending` і `Running` сервер не може довести, що призупинений обробник уже не відновиться, тому повертає `409`. Якщо операція залишилася `Pending`/`Running` після аварії, зупиніть усі екземпляри API й виконайте перевірений скрипт `ops/recover-ukrainealarm-webhook-operation.sql`, передавши UUID операції та глобального адміністратора. Скрипт переводить лише цю незавершену операцію в `Unknown` і додає запис аудиту. Якщо він не вивів `INSERT 0 1`, не продовжуйте; після успішного відновлення запустіть API, звірте фактичний стан у кабінеті провайдера та викличте `resolve`. Не виконуйте ручні SQL-зміни стану поза цим скриптом. Зміни поза Watcher відображайте через `state/reconcile`.

Запит і результат додаються до `audit_events`; токен, тіло відповіді провайдера та текст винятку не зберігаються. Намір фіксується до HTTP-виклику, результат — після нього. Між PostgreSQL і зовнішнім API немає спільної транзакції, тому `Unknown` потребує ручної звірки. API не повторює запит до провайдера автоматично. Відповіді admin endpoints не кешуються.

`POST /api/v1/alert-sources/ukrainealarm/webhook` приймає тіло до 8 KiB, не розбирає його й повертає `202 Accepted`. Сервер дозволяє до 10 запитів на хвилину з однієї IP-адреси; наступні відповіді — `429` із `Retry-After`. Новий сигнал повторної перевірки коалесціюється глобально в процесі й приймається не частіше ніж раз на 5 секунд. Метрика `ukrainealarm.webhook.requests` містить лише результат запиту (`accepted`, `rate_limited` або `too_large`), без IP чи тіла. Відкритий офіційний SDK описує в моделі реєстрації лише URL і не документує підпис callback, автентифікаційні заголовки або IP-діапазони відправника. Тому callback є недовіреним сигналом до повторної перевірки, а не доказом тривоги/відбою; цей endpoint не створює команди. Налаштуйте додаткове обмеження частоти на публічному reverse proxy.

Провайдер опитує `GET /api/v3/alerts/status` і порівнює `lastActionIndex`; коли індекс змінюється, він резолвить ID області/громади з `GET /api/v3/regions` за назвою й типом та читає статуси через `GET /api/v3/alerts/{regionId}`. ID UkraineAlarm не хардкодяться. Якщо callback приходить без просування індексу або індекс зменшується, наявний знімок стає `stale/unknown`; тіло callback не може його замінити. Наступні перевірки використовують зростальну паузу після помилок та повністю поважають `Retry-After` провайдера. Фоновий worker запускається разом із застосунком і реагує на callback, але не частіше одного upstream-опитування за хвилину. Поки немає спільної координації, запускайте один екземпляр Watcher: кілька реплік окремо опитуватимуть upstream.

API для створення й публікації сценаріїв ще немає. Поки адміністрування не реалізоване, чисте розгортання не містить доступних сценаріїв і пульт це явно показує. Вебпульт наразі запускає опубліковані сценарії; окремий елемент керування «Відбій» має передавати `targetCommandId` активного запуску.

`POST /api/v1/alert-commands` приймає дію `start` або `stop`; розмір тіла запиту не має перевищувати 16 KiB. Для обох дій потрібні 1–50 унікальних активних `locationIds` і UUID у заголовку `Idempotency-Key`. Для `start` потрібен опублікований `presetCode` із SHA-256 manifest hash у форматі 64 шістнадцяткових символів. Для `stop` потрібен `targetCommandId` опублікованої команди `start`; корпуси мають бути її цілями, а всі їхні активні пристрої мають перебувати в `InFlight`, `Accepted` або `Playing`. Перевірка формату hash не доводить, що аудіофайл наявний на вузлі. Повторне використання ключа тим самим користувачем дозволене лише з тією самою дією, сценарієм/цільовою командою і набором корпусів; порядок корпусів не має значення. Інше тіло для зайнятого ключа повертає `409 Conflict`. Команда, цілі, аудит і подія outbox зберігаються в одній транзакції. `expiresAtUtc` є обов’язковим полем команди: для операторської команди це п’ять хвилин від створення, для хвилини мовчання — рівно 09:01 `Europe/Kyiv` у день запуску. Споживач доставки й вузол зобов’язані відхиляти команду за `now >= expiresAtUtc` до початку відтворення. `InitiatedByUserId` є порожнім лише для системної команди; її перегляд дозволений глобальним адміністраторам і аудиторам. `202 Accepted` означає `Queued`, не фактичне виконання; фактичні стани надходять від вузла.

`POST /api/v1/alert-commands/{targetCommandId}/stop` створює окрему дію `stop` для вибраних корпусів вихідної команди `start`. Тіло містить 1–50 унікальних `locationIds`, що належать цільовій команді; потрібні чинна роль `admin` або `notificator` на кожен корпус, CSRF-токен та UUID `Idempotency-Key`. Вихідна команда має пройти outbox-матеріалізацію й мати підготовлені доставки для кожного корпусу; у кожному корпусі має лишатися принаймні один активний зареєстрований вузол. Якщо умова не виконана, API повертає `409 Conflict`; запит можна повторити після оновлення стану. Stop-команда та її точний набір вузлів вихідної доставки, цілі, аудит і outbox зберігаються однією транзакцією. До набору входять і вузли, що ще не отримали START: вищий `sequence` STOP не дозволяє відтворити запізнілий START. Якщо частина вузлів недоступна, запит усе одно доставляється решті, а недоступність видно у станах відповідних `CommandDelivery`; `202 Accepted` не означає успішну зупинку всього корпусу. Повтор ключа з тією самою цільовою командою та набором корпусів повертає ту саму команду; інша дія, ціль або набір повертають `409 Conflict`.

`202 Accepted` для START або STOP означає, що команда збережена й поставлена в доставку, а не що звук почався чи зупинився. Для STOP вузол надсилає `accepted` після прийняття команди та `stopped` після фактичної зупинки відтворення або безпечного no-op, якщо ціль уже не відтворюється. Сервер також приймає `completed` від сумісних клієнтів. Після успішної квитанції сервер атомарно завершує stop-доставку та переводить незавершену вихідну доставку START у `stopped`; уже термінальні стани START зберігаються. До квитанції UI має показувати очікування; втрата зв’язку не є підтвердженням зупинки. `expiresAtUtc` обмежує час доставки команди STOP п’ятьма хвилинами. Вузол має відхиляти команду за `now >= expiresAtUtc`.

`GET /api/v1/alert-commands/{id}` повертає `id`, `action`, nullable `presetCode` і `targetCommandId`, час створення та завершення строку дії, а також `targets` із корпусами й станами. Доступ має ініціатор команди або користувач із глобальною роллю `admin` чи `auditor`. Невідома команда й команда без прав для поточного користувача мають однакову відповідь `404`, щоб не розкривати існування запису; endpoint встановлює `Cache-Control: no-store`.

`GET /api/v1/alert-commands/{commandId}/deliveries` повертає сторінку доставок конкретної команди. Доступ мають її ініціатор або користувач із глобальною роллю `admin` чи `auditor`; системні команди без ініціатора доступні лише цим глобальним ролям. `page` нумерується від 1 і типово дорівнює 1; `pageSize` типово дорівнює 50 та має бути в межах 1–100. Відповідь містить `items`, `page`, `pageSize`, `totalCount`, `hasUnfinishedDeliveries` і `stateSummary`. Ознака незавершених доставок та кількість записів у `stateSummary` обчислюються за всіма доставками команди, а не лише поточною сторінкою. `stateSummary` містить кількість доставок кожного стану: `pending`, `inFlight`, `accepted`, `playing`, `completed`, `stopped`, `rejected`, `failed` і `expired`; сума цих значень дорівнює `totalCount`. `hasUnfinishedDeliveries` дорівнює `true`, якщо є стан `Pending`, `InFlight`, `Accepted` або `Playing`. Елементи стабільно впорядковані за `deviceId`. Дані елемента: `deviceId`, `deviceName`, `state`, `createdAtUtc`, `expiresAtUtc`, `lastAttemptAtUtc` та `attemptCount`. Відомості сертифіката пристрою не повертаються. Невідома команда й команда без прав для поточного користувача мають однакову відповідь `404`, щоб не розкривати існування запису; endpoint встановлює `Cache-Control: no-store`.

`POST /api/v1/device/command-receipts` приймає `CommandReceipt` лише від пристрою, визначеного за клієнтським сертифікатом mTLS. Watcher звіряє `commandId`, `sequence` і належність доставки цьому пристрою та його корпусу. `eventId` унікальний у межах пристрою: повтор тієї самої квитанції повертає `200` із `duplicate: true`, повтор ID з іншими даними — `409`. Неприпустимий перехід стану або sequence також повертає `409`; невідома доставка — `404`; некоректна схема чи код причини — `400`. `Rejected`, `Failed` та `Expired` вимагають короткий код причини з малих латинських літер, цифр і `_`, довжиною до 64 символів. Запис квитанції, зміна стану доставки та аудит зберігаються в одній транзакції.

`GET /api/v1/device/commands/stream` приймає лише WebSocket Upgrade на окремому порту `DeviceListener:Port` та вимагає чинний клієнтський сертифікат mTLS, прив'язаний до активного пристрою. Потік односторонній: сервер надсилає `CommandDispatch`, пристрій не надсилає прикладні повідомлення цим сокетом. Підтвердження й надалі передаються через описаний вище endpoint. Після тайм-ауту доставка повторюється з тим самим `commandId`; вузол відповідає за дедуплікацію перед запуском звуку.

Під час створення сервер атомарно призначає кожній цілі `sequence`, який зростає окремо в межах кожної локації. Для багатолокаційної команди лічильники блокуються у стабільному порядку UUID; команда, її номери й outbox фіксуються разом. Номери не повторюються після успішного commit, а пропуски допустимі після скасованої транзакції або історичного backfill. Порядок задає сервер, клієнт не передає і не змінює `sequence`.

`GET /api/v1/device/identity` працює лише на HTTPS-з’єднанні з обов’язковим клієнтським сертифікатом. ASP.NET Core перевіряє сертифікат і ланцюжок довіри, а Watcher звіряє його SHA-256 відбиток із незаблокованим пристроєм та активним корпусом у PostgreSQL. `deviceId` і `locationId` не приймаються від клієнта. Відповідь не кешується.

`GET /api/v1/audit-events` доступний у поточній версії API. Інші маршрути таблиці, для яких реалізацію не описано вище, залишаються цільовими.

`GET /api/v1/admin/devices` повертає сторінку зареєстрованих вузлів і доступний лише користувачам із чинним глобальним призначенням `admin` або `auditor`. Параметри `page` (від 1) і `pageSize` (1–100, типово 50) керують пагінацією. Сортування стабільне: назва корпусу, назва вузла, UUID вузла. Відповідь містить назву вузла й корпусу, ознаку відкликання, активність корпусу, ознаку відкритого WebSocket у локальному `DeviceCommandSessionRegistry` та nullable `lastSeenAtUtc` з останнього запису `device_sessions`. Відбиток сертифіката й інші облікові дані не повертаються; кешування вимкнено.

`isConnected` означає лише наявність живої WebSocket-сесії в реєстрі поточного процесу. За кількох реплік це не є глобальним станом кластера. Поле не підтверджує heartbeat, доступність підсилювача чи відтворення звуку. `lastSeenAtUtc` є часом із збереженої таблиці сесій; поки потік пристрою не оновлює її, значення може бути `null`.

Приклад запиту:

```json
{
  "action": "start",
  "presetCode": "evacuation",
  "locationIds": ["9ab5d623-80d7-48c3-99be-cbebdd9a535a"]
}
```

Клієнт не передає URL аудіо, шлях до файлу, рівень пріоритету чи особу ініціатора. Сервер бере ініціатора із сесії, а допустимі параметри — з опублікованого сценарію.

Відповідь `202 Accepted` означає, що команду записано й поставлено на доставку. Вона не є підтвердженням відтворення звуку; це підтверджують лише події стану від вузла.

## Події між Watcher і вузлом

DTO та назви подій визначаються в `Watcher.Contracts`; клієнти не дублюють їх як довільні рядки.

| Напрямок        | Подія                    | Обов’язкові дані                                                                                                                                                                                                          |
| --------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Watcher → вузол | `CommandDispatch`        | `schemaVersion`, `commandId`, `deviceId`, `locationId`, `sequence`, `action`, `issuedAtUtc`, `expiresAtUtc`; для `start` також `presetCode`, `manifestHash`, `maxPlaybackDurationSeconds`; для `stop` — `targetCommandId` |
| Вузол → Watcher | `CommandReceipt`         | `schemaVersion`, `eventId`, `commandId`, `sequence`, `state`, `occurredAtUtc`, код причини для відмови                                                                                                                    |
| Вузол → Watcher | `Heartbeat`              | `deviceId`, `sentAtUtc`, `audioState`, `configVersion`                                                                                                                                                                    |
| Watcher → вузол | `ConfigurationAvailable` | `version`, адреса переліку файлів, підпис                                                                                                                                                                                 |

Допустимі стани підтвердження: `Accepted`, `Playing`, `Completed`, `Stopped`, `Rejected`, `Failed`, `Expired`. Для `Rejected`, `Failed` і `Expired` потрібен код причини. Технічні подробиці не показуються кінцевому користувачу.

Для успішної команди `stop` пристрій передає `Completed` з ID команди зупинки. Сервер перевіряє її `targetCommandId` і в тій самій транзакції переводить активну доставку цільової команди `start` у `Stopped`. Стан `Stopped` у квитанції належить команді `start`, зупиненій локально або за таймером.

## Дедуплікація й порядок

1. Watcher створює команду, цілі локацій, запис аудиту й подію outbox в одній транзакції.
2. Вузол атомарно зберігає `command_id` у SQLite перед початком відтворення.
3. Повторно отримана команда повертає раніше збережений стан і не запускає звук знову.
4. `sequence` задає порядок у межах локації; UUID для цього не використовують.
5. Прострочена команда відхиляється і споживачем outbox, і вузлом до відтворення: перевірка виконується за `now >= expiresAtUtc`. Допустиме відхилення годин вузла задається окремо.

## Формат помилки

API повертає помилки у форматі Problem Details із кодом HTTP і `traceId`. Відповідь не містить стеку викликів, секретів, відбитків сертифікатів або подробиць мережі.
