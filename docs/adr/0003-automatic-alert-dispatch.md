# ADR 0003: Автоматичне оповіщення про повітряну тривогу

- Статус: Accepted; policy, транзакційний виконавець і статусний endpoint реалізовані. Автоматизація вимкнена за замовчуванням і вмикається лише серверною конфігурацією.
- Дата: 2026-11-05

## Контекст

Заклад розташований у Кременчуці. Watcher має відстежувати зміни підтвердженого стану повітряної тривоги та створювати команди оповіщення для налаштованих корпусів. Джерела мають різну географічну точність і не всі передають рівень тривоги. Застаріле, неповне або суперечливе спостереження не може безпечно створювати команду чи завершувати активний епізод.

## Рішення

1. Джерела вибираються за пріоритетом UkraineAlarm → NEPTUN → `alerts.in.ua`. Нижче пріоритетне джерело використовується, коли вище не має свіжого відомого спостереження для підтримуваної території. Свіже `partial`, `unknown` або `conflict` не є підтвердженим станом для дії. UkraineAlarm та `alerts.in.ua` залишаються на сервері; оператор бачить джерело, актуальність і географічну область спостереження.
2. Свіжий перехід `inactive` → `active` на тій самій території та від того самого вибраного джерела створює одну команду `start`. Активний стан, побачений під час першого запуску без baseline, лише ініціалізує baseline: стару тривогу не відтворюють. Після довгої перерви опитування активне спостереження також проходить повторну синхронізацію без запуску старої тривоги. Команда з простроченим строком дії не є підставою для відтворення.
3. UkraineAlarm і NEPTUN передають стан, але не червоний чи жовтий колір. Колір `red` або `yellow` береться лише з активного свіжого спостереження `alerts.in.ua`, коли його `DataUpdatedAtUtc` узгоджується в межах двох хвилин зі свіжим активним авторитетним спостереженням того самого рівня географії від UkraineAlarm або NEPTUN. Часткове, застаріле, суперечливе чи неузгоджене за часом спостереження кольору не підтверджується й не змінює рівень команди.
4. Для відкритого епізоду підтверджена зміна `red` ↔ `yellow` на тій самій території створює команду `replace`. Вона замінює активну команду епізоду, а не відкриває новий епізод. Для кожного кольору конфігурується окремий код опублікованого пресету (`AlertLevelPresets`); пресет має бути опублікований і мати валідний manifest hash. Якщо відповідного пресету немає або його перевірка не проходить, система утримується від команди й записує причину.
5. Початкове оповіщення без підтвердженого кольору використовує серверний `PresetCode`. Зокрема, UkraineAlarm і NEPTUN самостійно не можуть вибрати кольоровий пресет. Відсутність рівневого пресету для `alerts.in.ua` не підміняється іншим кольором.
6. Відкритий епізод завершується командою `stop` лише після свіжого `inactive`, який охоплює його географію: територія спостереження має бути тієї самої точності або ширшою. Активне спостереження на вужчій території зберігає епізод. Відсутній статус громади сам по собі не є відбоєм. Свіжі `unknown`, `partial`, `conflict`, застарілі дані, прогалина опитування чи неоднозначне географічне покриття утримують рішення; відсутність даних ніколи не перетворюється на STOP.
7. Команда створюється разом із цілями, outbox-повідомленням і записом аудиту в одній транзакції. Збережений стан епізоду та baseline забезпечують дедуплікацію між циклами опитування й екземплярами сервера. До аудиту потрапляють джерело, територія, рівень і час спостереження, але не токени чи сирі відповіді API.
8. Пристрій примусово завершує відтворення після налаштованої граничної тривалості. До перевірки цього обмеження на Windows-вузлі автоматичне створення команд не вмикається. Оператор зберігає право на ручну команду зупинки.

## Наслідки та операційні обмеження

- Автоматичне створення команд вимкнене за замовчуванням (`AlertSources:AutomaticDispatch:Enabled=false`). Увімкнення, інтервал опитування та пресети задаються серверною конфігурацією; клієнт не може змінити їх.
- Перед увімкненням опублікуйте й перевірте базовий пресет та окремі пресети для `red` і `yellow`, якщо потрібна передача кольорового рівня. Перевірте manifest hash, наявність аудіо на вузлах, маршрут, фізичну чутність і підтримку `replace` вузлами.
- Зміна кольору залежить від доступності двох свіжих джерел зі спільним рівнем географії та узгодженими часовими мітками. Якщо corroboration немає, чинний епізод зберігається; автоматизація не вгадує колір і не перемикає пресет.
- Під час холодного старту й після перерви опитування сервер синхронізує спостереження без повторного запуску вже активної тривоги. Відповідальний оператор має перевірити офіційний поточний стан; цей режим може не створити автоматичну команду для тривоги, що почалася під час недоступності Watcher.
- Вимкнення автоматизації припиняє створення нових автоматичних команд, але саме по собі не надсилає STOP для відкритого епізоду. Оператор має перевірити стан і за потреби відправити ручний STOP. Доставка команди `start`, квитанція `Playing` і фізична чутність сигналу — різні стани, які перевіряються окремо.
- Моніторинг джерел, policy та транзакційний виконавець є окремими компонентами. Помилка зовнішнього API не закриває епізод. Після відновлення бази з копії перед увімкненням перевірте збережений baseline, відкритий епізод і доставки, щоб не створити повторну дію.
- Оповіщення закладу є додатковим каналом. Офіційні канали цивільного захисту залишаються основним джерелом інструкцій для людей.
