# ADR 0008: Доставка команд на пристрої корпусів

- Статус: Proposed
- Дата: 2026-11-05

## Контекст

Watcher уже зберігає команду, цілі за корпусами, outbox і аудит, але не має транспорту до Windows-вузла. Один корпус може мати кілька пристроїв. Відповідь API `202 Accepted` підтверджує лише запис наміру в базу; фактичне відтворення має окреме підтвердження.

## Рішення

1. `CommandTarget` зберігає намір для корпусу. Для кожного зареєстрованого пристрою корпусу створюється окремий `CommandDelivery` з унікальною парою `(command_id, device_id)`, станом, часом останньої спроби й наступної спроби. Кілька процесів Watcher узгоджують видачу через транзакційне захоплення PostgreSQL; мережевий виклик відбувається поза транзакцією.
2. Кожна команда отримує серверний `command_id`, послідовний номер у межах корпусу, `issued_at_utc`, `expires_at_utc` і контрольну суму опублікованого маніфесту. `expires_at_utc` обмежує початок відтворення; максимальна тривалість відтворення є окремою межею. Після закінчення строку доставка переходить у `Expired` і більше не повторюється.
3. Пристрій автентифікується власним сертифікатом mTLS. Сервер звіряє сертифікат із чинним записом пристрою та сам визначає його `device_id` і корпус. Дані в повідомленні не можуть підмінити цю прив'язку. Відкликання пристрою припиняє нові доставки й активні сеанси.
4. Windows-служба перевіряє версію контракту, корпус, послідовність, строк дії, локальний маніфест і хеш аудіофайлу. Вона записує `command_id` у локальну SQLite транзакцію **до** запуску звуку. Повторна доставка повертає збережений результат і не запускає звук вдруге. Без зв'язку з Watcher локальний таймер припиняє циклічний звук після встановленої максимальної тривалості.
5. Підтвердження мають стани `Accepted`, `Playing`, `Completed`, `Stopped`, `Rejected`, `Failed`, `Expired`. `Accepted` не означає, що звук уже відтворюється. Сервер приймає підтвердження лише від пристрою, якому призначено доставку, перевіряє допустимий перехід і атомарно записує стан та аудит. Після відновлення зв'язку вузол повторно надсилає збережені підтвердження.
6. Зупинка є окремою командою з посиланням на `target_command_id`. Вузол зупиняє лише відповідне активне відтворення. Повторна зупинка безпечна; пізній `start` не може обійти новішу команду `stop` завдяки номеру послідовності.
7. Вузол генерує `event_id` один раз для кожного логічного підтвердження та зберігає його під час повторного надсилання. Сервер забезпечує унікальність `(device_id, event_id)`. Для `Rejected`, `Failed` і `Expired` обов'язковий короткий код причини без тексту винятку.
8. Послідовність зростає для кожного корпусу при створенні команди, а не при пізнішій обробці outbox. Пропуски номерів допустимі. Навіть зупинка, для якої вже немає активного звуку, просуває збережений на вузлі номер; після неї команда `start` з меншим номером відхиляється.

## Наслідки

- Потрібні окремі міграції для доставок, порядкових номерів і станів, серверний transport із mTLS та Windows Worker Service з локальним журналом SQLite.
- Видача outbox має повторювати тимчасові помилки лише до `expires_at_utc`; підтвердження й фактичний стан відтворення показуються оператору окремо.
- До впровадження перевірки строку дії й локального обмеження тривалості на вузлі автоматичний запуск звуку не вмикається.
