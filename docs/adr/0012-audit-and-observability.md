# ADR 0012: Аудит дій і спостережуваність

## Статус

Прийнято.

## Контекст

Watcher керує критичними командами оповіщення. Потрібно встановити, хто створив або змінив дію, які локації та сценарій було обрано, яку спробу надсилання зафіксував сервер і яку квитанцію надіслав кожен вузол. HTTP `202 Accepted` не доводить доставку. Квитанція `Playing` підтверджує запуск програмного шляху відтворення на вузлі, але без акустичного loopback або датчика не доводить, що звук фізично вийшов із динаміка. Одночасне логування кожного heartbeat і частого polling створює шум і зайве навантаження.

## Рішення

- Розділити довготривалий аудит у PostgreSQL, структуровані runtime logs і агреговані метрики.
- Зберігати аудит значущих дій та переходів стану з суб’єктом, ціллю, UTC-часом, результатом і безпечними ідентифікаторами кореляції.
- Пов’язувати повний життєвий цикл за `commandId`, а доставку — також за `deviceId`, `locationId` і номером спроби.
- Розрізняти серверне прийняття, `delivery_attempt_started`, результат WebSocket-запису `completed`/`not_started`/`indeterminate`, квитанцію `Accepted`, програмний стан відтворення `Playing` і завершальний результат вузла. `completed` підтверджує лише завершення виклику запису; `not_started` означає, що виклик не починався; `indeterminate` після помилки, тайм-ауту або скасування виклику через зупинку сервісу може означати часткове передавання й потребує звірки з квитанцією. Якщо результат не збережено до аварійного завершення процесу, стан лишається невизначеним. `InFlight` не підтверджує фактичне передавання; `Expired` у доставці може бути виставлений сервером без квитанції вузла. Успіх агрегується по вузлах без приховування часткової невдачі.
- Зберігати обраний `PresetCode`; для автоматичних подій також фіксувати нормалізований `AlertLevel`, джерело, область/обсяг і час спостереження від провайдера. `SoundPreset.Priority` залишається лише сортуванням сценаріїв у UI й не входить до контракту відтворення. Фізичне підтвердження звуку або його гучності потребує окремого обладнання та контракту.
- Для `automatic_alert.held` обмежувати масив нормалізованих спостережень 24 елементами, явно позначати обрізання через `ObservationsTruncated` і не копіювати сирі відповіді провайдерів.
- Записувати стан та аудит однією транзакцією там, де вони утворюються в одній операції; ідемпотентно обробляти повторні квитанції.
- Часті успішні heartbeat, polling і порожні проходи черги вимірювати метриками або журналювати з низьким рівнем; значущі помилки й переходи залишати в runtime logs.
- Не записувати токени, секрети, сирі payload провайдерів, аудіодані чи надлишкові персональні атрибути.
- Залишити політику retention і архівації явним експлуатаційним рішенням; не видаляти аудит автоматично до його затвердження.

## Наслідки

- Розслідування інциденту може відрізнити прийняття команди від звіту вузла про запуск програмного відтворення; воно не підтверджує фізичне звучання без окремого датчика.
- Durable audit росте відповідно до кількості суттєвих переходів; heartbeat та регулярний polling не множать записи `audit_events`.
- Резервні копії мають узгоджено охоплювати аудит, команди, доставки й квитанції.
- Перед production потрібні перевірка повноти подій, правила runtime log rotation і погоджений строк зберігання.
