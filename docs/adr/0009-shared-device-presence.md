# Спільний стан присутності вузлів

## Статус

Прийнято.

## Контекст

Watcher може працювати в кількох репліках за балансувальником. Локальний `DeviceCommandSessionRegistry` потрібен для надсилання команд сокетам, але не може бути джерелом стану підключення для API: запит панелі може потрапити в іншу репліку. У `device_sessions` уже є часові поля підключення, останньої активності й відключення.

## Рішення

- Зберігати стан кожного WebSocket-сеансу в `device_sessions`; не додавати таблиць чи міграцій.
- Записувати heartbeat кожні 5 секунд і вважати вузол підключеним, якщо сеанс не завершений та heartbeat молодший за 20 секунд.
- При відкритті нового сеансу блокувати відповідний рядок `devices` транзакцією PostgreSQL, завершувати попередні активні сеанси та створювати новий. Це серіалізує reconnect-и, що надійшли на різні репліки.
- Heartbeat оновлює лише власний незавершений сеанс. Якщо оновлено нуль рядків, інша репліка його замінила, тож сокет закривається.
- Під час штатного завершення позначати сеанс відключеним. Після аварії репліки присутність природно спливає за TTL.
- Обидва API стану читають присутність із бази. Локальний реєстр лишається лише транспортним маршрутизатором команд.
- Перед вибором локального сокета транспорт звіряє його ідентифікатор сеансу зі спільним активним записом, щоб стара репліка не продовжувала доставку після reconnect на іншій репліці.
- Увімкнути WebSocket keep-alive із 15-секундним інтервалом і 30-секундним тайм-аутом очікування відповіді.

## Наслідки

- Панелі бачать однаковий стан з будь-якої репліки без sticky sessions.
- PostgreSQL отримує один невеликий запис оновлення на пристрій кожні 5 секунд; TTL допускає короткий розрив мережі перед переходом у стан offline.
- Якщо БД недоступна під час heartbeat, сокет закривається, а стан після збоїв обмежений TTL.
- Збереження історії сеансів потребує періодичної retention-політики, яку слід визначити окремим рішенням після вимірювання обсягу.
