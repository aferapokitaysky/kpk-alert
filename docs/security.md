# Безпека

## Що система має захищати

Ключові активи: право запуску й зупинки сигналів, пристрої в корпусах, затверджені аудіофайли, ролі користувачів, сертифікати вузлів та історія дій. Браузер користувача й зовнішні джерела тривог перебувають за межами довіри системи.

## Вхід із Academica

Watcher створює власну серверну сесію. Спільна сесійна cookie на всі піддомени `kgta.edu.ua` збільшує наслідки компрометації будь-якого з них, тому перехід із журналу виконується через одноразовий код:

1. Авторизований користувач натискає посилання на Alert в Academica.
2. Сервер Academica створює одноразовий код для конкретного одержувача й адреси повернення.
3. Watcher обмінює код через серверний канал, перевіряє підпис, видавця, одержувача, строк дії, nonce та повторне використання.
4. Watcher перевіряє власні права користувача й створює host-only cookie з `Secure`, `HttpOnly`, `SameSite=Lax`.

Код живе не більше 60 секунд, використовується один раз і не містить зайвих даних користувача. Він не записується в журнали. Звичайний вхід використовує погоджений механізм Google OAuth; Google підтверджує особу, а права призначаються в системі.

## Облікові дані вузлів

- Для кожного вузла випускається окремий клієнтський TLS-сертифікат, прив’язаний до конкретної локації.
- Сертифікати мають процедуру ротації та відкликання; мережеве з’єднання використовує mTLS.
- Секрет первинного сполучення є тимчасовим і відкликається після видачі сертифіката.
- Приватний ключ на Windows захищається DPAPI та правами облікового запису служби.
- Дозволені IP-адреси й обмеження частоти доповнюють перевірку сертифіката, але не замінюють її.

## Ролі та дозволи

| Роль | Дозволені дії |
| --- | --- |
| `admin` | Користувачі, ролі, пристрої, сертифікати й локації |
| `sound_engineer` | Підготовка, перевірка та публікація аудіосценаріїв |
| `notificator` | Запуск і зупинка дозволених сценаріїв у призначених локаціях |
| `auditor` | Перегляд стану системи й журналу |

Watcher перевіряє роль, стан облікового запису, доступ до локації та доступність сценарію під час кожного запиту. Приховування кнопок в інтерфейсі не є контролем доступу.

Google OAuth приймає лише підтверджену Google адресу й активний обліковий запис, попередньо зареєстрований у Watcher за незмінним зовнішнім subject. Реєстрація нових користувачів через самостійний вхід вимкнена. Секрети OAuth задаються через змінні середовища deployment-системи.

Для браузерних змінних запитів потрібні anti-forgery перевірка й перевірка походження запиту. Політика CSP обмежує джерела виконуваного вмісту. CORS заборонено, крім явно погоджених адрес панелі.

## Аудіофайли та команди

- Вузол відтворює лише локальні файли з опублікованого переліку.
- Для кожного файлу зберігається SHA-256; вузол перевіряє його перед відтворенням.
- Сервер не надсилає URL, шлях до диска чи команду оболонки.
- Тип і розмір завантаження перевіряються сервером; ім’я файлу формує сервер.
- Команди мають строк дії, ідентифікатор для дедуплікації та запис аудиту.

## Секрети та середовище

Секрети надходять із захищеного сховища середовища розгортання. Їх не додають до Git, образів Docker, прикладів конфігурації чи журналів. Резервні копії бази шифруються; процедуру відновлення регулярно перевіряють.

## Аудит і реагування

Журналюються вхід і невдалі спроби, зміни ролей, сполучення та відкликання вузлів, запуск/зупинка сценарію, підтвердження доставки, помилки аудіо й робота резервного сценарію. Запис містить особу або пристрій, час UTC, тип дії, результат і кореляційний ідентифікатор. Токени й секрети не журналюються.

У разі підозри на компрометацію відкликають відповідну сесію або сертифікат, блокують пристрій чи обліковий запис і зберігають журнали для перевірки. Звичайні адміністративні функції не видаляють записи аудиту.

## Заборонені рішення

- зберігати довготривалі токени в `localStorage`;
- вважати IP-адресу достатнім доказом особи пристрою;
- приймати від клієнта команду операційної системи чи довільний медіашлях;
- застосовувати неперевірений файл або конфігурацію;
- запускати сирену автоматично за неузгодженим джерелом.
