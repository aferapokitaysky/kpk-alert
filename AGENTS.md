# Правила роботи в репозиторії

Це система оповіщення закладу. Зміни мають бути зрозумілими, перевірюваними та придатними до супроводу. Документація, коментарі до коду й увесь видимий користувачеві текст пишуться українською. У чаті мову узгоджуємо окремо.

## Перед початком

1. Перевір поточну гілку, `git status`, структуру сусідніх модулів, налаштування інструментів, CI й наявні тести.
2. Знайди готовий компонент або правило, перш ніж створювати новий аналог.
3. Не перезаписуй незакомічені зміни користувача й не включай їх у свою задачу.

## Гілки та Git Flow

- `main` містить перевірені стабільні випуски.
- `develop` — спільна гілка розробки.
- Самостійна задача виконується у власній гілці від актуального `develop`.
- Назви гілок: `feature/korotka-nazva`, `fix/korotka-nazva`, `docs/korotka-nazva`, `release/x.y.z`, `hotfix/korotka-nazva`.
- Не працюй безпосередньо в `main` чи `develop`.
- Зміни проходять через PR у `develop`; реліз у `main` — окремим PR після перевірок.

## Коміти

- Пиши українською або російською, коротко й конкретно; для цього репозиторію бажана українська.
- Один коміт має відповідати одному зрозумілому кроку роботи.
- Не використовуй порожні повідомлення на кшталт `Update`, `Changes`, `WIP`, `Fix stuff`.
- Не дроби історію на формальні мікрокоміти й не об’єднуй незалежні зміни в один великий коміт.
- Приклади: `Додано схему бази даних`, `Описано вхід із Academica`, `Виправлено повторний запуск команди`.

## Структура й межі модулів

- Кожна самостійна функція має зрозумілу межу в `src/` і власні тести.
- Не створюй порожні шари, узагальнені папки `misc`/`common-final` і абстракції без повторного використання.
- API-контракти зберігай у визначеному проєкті контрактів; схему PostgreSQL змінюй міграціями.
- Залежності доменних правил не мають вести до вебінфраструктури чи файлової системи.
- Надавай перевагу явним станам і результатам операцій; не ховай помилки загальними `catch`.

## Стиль C# та .NET

- Цільова платформа — .NET 8 або узгоджена підтримувана версія; точні SDK фіксуються в `global.json` після створення solution.
- Дотримуйся `.editorconfig`, nullable reference types і попереджень компілятора без необґрунтованого вимкнення.
- Типи й публічні члени мають предметні назви; async-методи завершуються на `Async` і приймають `CancellationToken`, коли операція може тривати.
- Не використовуй `async void`, `.Result`, `.Wait()`, приховану глобальну mutable-станцію та `catch { }`.
- Вхідні DTO перевіряй на межі API; бізнес-інваріанти перевіряй у доменному/Application-рівні.
- Не повертай stack trace чи внутрішні винятки користувачеві.

## Стиль TypeScript і React

- Для клієнтського коду використовуй TypeScript зі `strict: true`; не додавай JavaScript там, де достатньо TypeScript.
- Не використовуй `any`, `@ts-ignore` або приведення типу без поясненої необхідності.
- Компонент має одну відповідальність; стан завантаження, помилки й порожнього результату описуй явно.
- Не запускай важливу дію з клікабельного `div`; використовуй семантичну кнопку, форму й коректні підписи полів.
- Не вважай клієнтське приховування кнопок перевіркою дозволу.

## Форматування й інструменти

- Форматування C# виконується `dotnet format`; стиль фронтенду визначають ESLint і Prettier після додавання відповідних конфігурацій.
- Не додавай formatter або аналізатор без узгодження єдиного стандарту та команди CI.
- Для JSON і YAML дотримуйся 2 пробілів; для Markdown — короткі заголовки, таблиці лише для порівнянь, перевірені посилання.
- У CI мають виконуватися форматування з перевіркою, збірка, тести та перевірка документації.

## Мова й тексти інтерфейсу

- Документація, коментарі й увесь UI — українською.
- Пиши просто: назва кнопки описує дію, помилка пояснює, що сталося і що можна зробити.
- Не використовуй рекламні формули, штучну бадьорість, зайві емодзі, `Упс!` і неясне `Щось пішло не так`.
- Стани «Команду прийнято» й «Сигнал відтворюється» мають різні назви й значення.

## Стиль UI

- Орієнтуйся на дизайн Academica: Inter, синя палітра KPK, жовтий акцент, світлі поверхні, стримані межі, радіуси й поля форм.
- Перед зміною UI звір актуальні компоненти й CSS журналу; деталі наведені в `docs/ui-journal.md`.
- Екстрені дії вирізняються кольором і розміром, але зберігають типографіку, геометрію та керування фокусом системи.
- Перевіряй мобільний, планшетний і desktop-розміри; не покладайся лише на колір; поважай `prefers-reduced-motion`.

## Безпека

- Не додавай до Git паролі, токени, сертифікати, приватні ключі, реальні IP, персональні дані чи production-конфігурацію.
- Не приймай від клієнта довільний URL або шлях аудіофайлу, пріоритет чи особу ініціатора.
- Кожна команда має `command_id`, перевірку права, термін дії, запис аудиту й дедуплікацію на вузлі.
- Повторна доставка команди не може вдруге запускати звук.
- Зовнішні відповіді, назви файлів і дані з мережі вважай недовіреними.
- Не послаблюй mTLS, автентифікацію, RBAC, CSRF-захист або аудит заради швидшої демонстрації.

## Тести та перевірки

- Нову логіку перевіряй автоматизованими тестами; для виправлення дефекту додай тест, що відтворює проблему.
- Перевіряй успішний сценарій, відмову, межові значення й права доступу, якщо вони впливають на поведінку.
- До PR запускай усі наявні перевірки. Не заявляй про проходження команд, яких ще немає в репозиторії.
- Не видаляй тест, щоб приховати дефект, і не ігноруй попередження без зафіксованої причини.

## PR та рев’ю

- PR має одну мету, короткий опис українською, пов’язані зміни, спосіб перевірки та відомі обмеження.
- Рев’юер перевіряє поведінку, безпеку, міграції, журнали, відновлення після збоїв і мобільний вигляд.
- Не зливай PR із червоними обов’язковими перевірками; не обходь захист гілок і не переписуй спільну історію примусовим push.
- Архітектурні рішення з довгими наслідками записуй у `docs/adr/`.

## Заборонено

- Комітити секрети, завантажені залежності, збіркові артефакти чи локальні бази.
- Зберігати довготривалі сесійні токени у `localStorage`.
- Видаляти записи аудиту штатною операцією чи автоматично відтворювати старі команди після відновлення копії.
- Додавати функцію, яку неможливо безпечно пояснити оператору та перевірити під час рев’ю.
